The pr-sentinel activity report below is generated by re-reading what Claude
Code already recorded in your local session transcripts. It adds no telemetry
and makes no network call — see PRIVACY.md. Show it to me verbatim, then add at
most two sentences naming what stands out. Do not edit any files.

The report answers three questions:

- **Nudges fired vs watchers launched** — the follow-through rate. The nudge is
  advisory: a hook cannot make the model call a tool. A rate well below 100%
  means sessions are being told to watch and not doing it. Read it with the
  Stop-hook backstop line underneath: a high rate beside a non-zero backstop
  count means the backstop is what got those watchers launched, not the nudge.
- **Watcher events by kind** — `work` events (`check_failure`, `conflict`,
  `behind`, `dequeued`, `blocked`) are the plugin earning its keep; `done`
  (`ready`, `closed`) means the PR needed no babysitting. A high `degraded`
  count (`timeout`, `error`) means watches are ending with no verdict — raise
  `PR_SENTINEL_TIMEOUT`, or check that `gh` is authenticated.
- **Events by repository** — where the CI time actually goes.

Two numbers are worth reading carefully rather than at face value:

- **Foreground launches.** A watcher that was not backgrounded pinned the main
  thread, which is the anti-pattern the plugin replaces. Any non-zero count here
  is worth chasing to the session that did it.
- **Nudges naming no PR number.** These are branch pushes where the hook could
  not resolve a PR, so they are reported apart and left out of the
  follow-through rate — they are not unanswered nudges.

The default window is 7 days. pr-sentinel activity is bursty, so pass
`--since 30d` or `--since all` if the window comes back thin.
