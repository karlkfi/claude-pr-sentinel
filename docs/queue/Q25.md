# A newline does not separate simple commands in the guard's tokenizer

`simple_commands` in `scripts/pr-sentinel-guard.py` documents itself as
splitting on "`&&`, `||`, `|`, `;`, `(`, `)`, newlines", and it does not split
on newlines: `shlex` consumes `\n` as whitespace before it can reach
`punctuation_chars`, so every line of a multi-line command lands in one group
and only the first line's leading word is ever read as a command word.

Measured 2026-08-19, loading the guard and calling it directly. Taken against
`main` at f6d140d and re-taken at 632f1f8, where `pr-sentinel-guard.py` is
byte-identical:

```
"git status; gh run watch 9"    classify_poll -> 'gh_run_watch'   (denied)
"git status\ngh run watch 9"    classify_poll -> None             (allowed)
```

A poll on the second line of a multi-line Bash call is the ordinary shape, not
a contrived one, so this is the poll deny's main evasion path and it is reached
by accident rather than on purpose.

## It disables the overlap deny on the normal path

Both denies read the same `simple_commands`, and the create side is where the
consequence has been observed end to end rather than inferred. A `gh pr create`
was allowed while two open PRs genuinely overlapped the branch, and the probe
was not the problem: `overlapping_prs` returned both PRs in 2.44s, inside its 5s
budget. The guard reached no verdict because it never recognised the create.

Measured 2026-08-19 with `tool_name: "Bash"` present, against `main` at
bea581e:

```
gh pr create --fill                        is_pr_create -> True    (deny)
echo hi; gh pr create --fill               is_pr_create -> True    (deny)
echo hi<newline>gh pr create --fill        is_pr_create -> False   (allowed)
cat >> body.md <<'MD' … MD                 is_pr_create -> False   (allowed)
  <newline>gh pr create --body-file body.md
```

That last shape is how an agent composes a PR body, so the overlap deny is off
on close to the normal path rather than on an edge case. The heredoc tokenizes
to one group, `['MD', 'x', 'MD', 'gh', 'pr', 'create', …]`, headed by the wrong
word.

Credit for the end-to-end case: it fired on a sibling session's own `gh pr
create` and they measured it rather than working around it.

It cuts the other way too, and this row was written by walking into it. A
`git commit -F -` whose message quotes a poll command is denied, because the
heredoc body is tokenized as shell rather than as the text the command writes:
the guard read the message's own example out of the body and refused the commit.
So the same tokenizer both misses a real poll on a second line and blocks a
commit that only talks about one.

The escape hatch inverts the same way: an inline `PR_SENTINEL_OVERRIDE=` prefix
on a second line is not honoured, because the assignment is no longer `argv[0]`.
The activity report counts that command as an override — it splits on newlines
itself — so the two disagree until this is fixed.

## The fix already exists, for the other copy

`simple_commands` is duplicated — once at
`scripts/pr-sentinel-guard.py:167:def simple_commands(command):` and once at
`scripts/pr-sentinel-hook.py:86:def simple_commands(command):`.

PR #78 (issue #76) fixes exactly this bug in the hook's copy, with the same
diagnosis, in one line inside the `shlex` setup:

```python
lex.whitespace = lex.whitespace.replace('\n', '')
```

It does not touch the guard's, and the guard's is the one behind both denies.
Applying that line to the guard's copy fixes the tokenization — confirmed by
running the same `shlex` setup with and without it:

```
without:  [['echo', 'hi', 'gh', 'pr', 'create', '--fill']]
with:     [['echo', 'hi'], ['gh', 'pr', 'create', '--fill']]
```

So the work is either that line plus the shape table above as its tests, or
de-duplicating the two copies — which is arguably the real defect, since one of
them has now been fixed alone.

## Why a reviewer would close this without fixing it

`\n` is right there in `punctuation_chars` and the docstring claims the split,
so the argument list reads as correct and the declared behaviour matches the
intent. Nothing at the call site suggests checking whether `shlex` actually
emits a newline token — it does not, because `whitespace` still contains `\n`
and is consulted first. Declared, never emitted. That is the fact to keep in
front of anyone triaging this.
