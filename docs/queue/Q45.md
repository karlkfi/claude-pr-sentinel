# The Stop hook compares an unordered failed-check set as an exact string

The Stop hook's livelock guard identifies "which occurrence of an event is
this" by an exact-string tuple
(`scripts/pr_sentinel_stop_hook.py:382:def _report_signature(text):`), whose
middle element is the `Failed checks:` line verbatim
(`scripts/pr_sentinel_stop_hook.py:185:FAILED_CHECKS_RE = re.compile(r'Failed checks:[ \t]*([^\n]*)')`).
Two runs dampen only when their tuples are equal
(`scripts/pr_sentinel_stop_hook.py:693:        repeated = next((sig[0] for sig, runs in sig_launches.get(pr, {}).items()`).

That line is built by appending each failing check in the order `gh pr checks`
returned it
(`scripts/pr-sentinel-watch.sh:1027:							failed_names="${failed_names:+$failed_names, }${name} (${bucket})"`),
and that order is GitHub's, not the watcher's: the read is a bare `.[]` over
`gh pr checks --json`, with no sort anywhere between it and the report
(`scripts/pr-sentinel-watch.sh:352:	gh pr checks "$PR" --json name,bucket,link`).
The comparison is therefore
exact-string against a source with no defined order: two watcher runs over an
unchanged head, reporting an unchanged set of failures, can produce two
signatures that never match, and the dampening they exist to trigger never
fires.

## What was observed

Measured 2026-09-09 on pr-sentinel 0.9.0 against
`actions-gateway/github-actions-gateway` PR #1890, four watcher launches at one
head (`d5c8b84ad4669bf9ff0740b105635e2ca6a0135d`, nothing pushed between them).
Read from that session's transcript, `Failed checks:` line per run:

1. 17:15:51Z — `trivy (agc, 1) (fail), trivy (gmc, 1) (fail)`
2. 17:20:19Z — `security-scan-gate (fail), trivy (agc, 1) (fail), trivy (gmc, 1) (fail)`
3. 17:20:55Z — `security-scan-gate (fail), trivy (agc, 1) (fail), trivy (gmc, 1) (fail)`
4. 17:21:27Z — `security-scan-gate (fail), trivy (gmc, 1) (fail), trivy (agc, 1) (fail)`

Runs 2 and 4 hold the identical three checks and differ only in the order of
the two `trivy` rows, so they are two distinct signatures. Runs 2 and 3 do
match, which is why nothing livelocked here — the guard survived on the
membership staying still for two consecutive polls rather than on the rule
being sound. Had the order alternated, no pair would ever have matched.

Run 1 differs by membership, not order: `security-scan-gate` had not failed
yet. That difference is real and the signature is right to treat it as a
different occurrence.

## Proposal

Candidates, not a prescription.

- **Compare the failed set as a set.** Split the line on `, ` and compare the
  sorted tuple, in `_report_signature` only. Confined to the hook, changes no
  report, and needs no watcher release to take effect on watchers already
  installed.
- **Order the set where it is written.** Sort `failed_names` in the watcher, so
  the report itself is stable and the hook's exact-string compare becomes
  sound. Better output — a stable line is easier for a human to diff across two
  reports — but it only helps once the watcher writing the report is new
  enough, and the hook still faces old reports in a live transcript.

Doing both is defensible: the watcher stabilises what it emits, the hook stops
depending on it having done so.

Whichever lands needs a test that would fail today — two reports with the same
membership in different orders, asserted to dampen. `tests/test_stop_hook.py`
already drives the hook from synthetic transcripts, so the fixture is a
reordering of one that exists.

## Out of scope

Not the base-comparator staleness measured on the same PR (fixed separately:
`check_failure` now names the base run and its age). This row is only about
whether two reports of the *same* state compare equal.
