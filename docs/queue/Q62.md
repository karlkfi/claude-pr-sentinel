# An unbalanced quote silently disables the overlap deny

The guard's tokenizer returns no groups for a command string it cannot lex, and
every branch then reads as "not my business": `is_pr_create` is False,
`classify_poll` is None, and the guard defers. That is the fail-safe direction
and it is deliberate —
`scripts/pr_sentinel_guard.py:213:def simple_commands(command):` says a string
shlex rejects "comes back empty so the caller defers — this side denies, and a
deny on a parse we could not make is the wrong direction."

What it costs is not visible from inside the guard. A `gh pr create` whose body
text carries an apostrophe is unlexable, so the overlap deny cannot fire for it
— and a `gh pr create` carrying prose is the ordinary shape, not an exotic one.

## Measured

2026-09-19, one workstation, the 7-day window of the local corpus, using the
override split added for Q33. Of 27 inline `PR_SENTINEL_OVERRIDE=` prefixes,
three landed on commands the guard had already deferred on:

| reading | all three |
|---|---|
| `tokenize.lex(command)` | `ValueError: No closing quotation` |
| `simple_commands(cmd)` (strict, what the guard calls) | `0` groups |
| `simple_commands(cmd, lenient=True)` | 8, 9 and 10 groups |
| `_is_gh_pr_create` over the lenient groups | **True for all three** |

Shapes only, since the commands carry real paths: each was a 3–6 KB chain
writing a PR body through a heredoc and then creating the PR, two opening with
a `VAR=<path>` assignment and one with `cat`.

So the lenient parse finds the create the strict one misses, in every case
measured. The three sessions each wrote a considered override reason for a deny
that could not have fired.

## Two defects, and they want different answers

**The overlap check is absent where it is most wanted.** A create with a long
prose body is exactly the create most likely to be a real PR, and the quote that
disables the check is likely to be an apostrophe in that prose. This is the
inverse of the deny the guard was written around: not a wrong refusal, a silent
non-refusal.

**A defer is silence, so the author cannot tell the two apart.** Nothing
distinguishes "the guard considered this and had no opinion" from "the guard
would have denied and my prefix stopped it". Sessions spend a deliberate escape
hatch on the first believing it is the second, and no reading available to them
corrects it.

## Not obviously "switch the guard to lenient"

The PostToolUse hook already does —
`scripts/pr_sentinel_hook.py:68:    return tokenize.simple_commands(command, lenient=True)`
— and that is safe there because the hook only nudges. The guard denies, so
leniency buys coverage at the cost of denying on a parse it could not make
cleanly, which is the thing its own comment rules out. A line-by-line retry is
also not the same parse: it can put a word in command position that the real
shell never would.

Worth weighing against a narrower shape: keep the strict parse for the deny, and
use the lenient one only to decide whether to *look*, so an unlexable string
that leniently contains a `gh pr create` is reported rather than denied. That
keeps the fail-safe property and removes the silence.

Whichever way it goes, the override count for this shape should stop reading as
friction the guard caused: it is friction the guard's silence caused.
