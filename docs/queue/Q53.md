# A check name can contain the separator the failed set is joined with

The watcher joins failing checks with `, ` and appends each check's bucket in
parentheses
(`scripts/pr-sentinel-watch.sh:1119:							failed_names="${failed_names:+$failed_names, }${name} (${bucket})"`).
A check **name** may itself contain that separator, so the line does not say
where one check ends and the next begins:

    Failed checks: security-scan-gate (fail), trivy (agc, 1) (fail)

That is two checks. Split on `, ` and it is four fragments, none of which is a
check. The names are GitHub's — a matrix leg renders as `trivy (agc, 1)` — so
this is the ordinary shape for any matrixed job, not a contrived one. The same
data appears in the transcript measured for the ordering defect (shipped
2026-09-18), where it went unremarked because nothing there needed to parse
it.

## Nothing is known to be broken by it today

Both current readers compare the line for **equality** rather than parsing it,
and equality survives the ambiguity: two renderings of one set yield the same
fragments, so a sorted multiset compares equal whatever the names contain. The
Stop hook's `_failed_set` does exactly that and carries a test that two
genuinely different sets do not collide through the split.

So this is a latent defect, filed because the line reads like a list and the
next reader will treat it as one. The cost lands on whoever writes a consumer
that needs the individual checks — counting them, matching one against a
required-check list, or rendering them — and discovers the line cannot support
it, most likely after shipping something that works until a matrix leg fails.

## Options

- **Leave it, and say so where it is built.** Cheapest. A comment at the join
  stating the line is a display string and not a parseable list, and that
  equality is the only supported operation on it. Fixes nothing; stops the next
  reader assuming.
- **Emit a machine-readable field beside it.** Keep `Failed checks:` for humans
  and add a second line with an unambiguous encoding (one check per line under a
  header, or a separator no name can contain). Costs report surface and a
  watcher release before any reader can use it, and the Stop hook reads reports
  written by older watchers indefinitely, so both forms have to be tolerated.
- **Change the separator.** Narrowest, and the trap: it only moves the problem
  unless the replacement is genuinely impossible in a GitHub check name, which
  needs checking rather than assuming.

Whichever lands, the equality path must keep working against reports already
written in a live transcript — that constraint is what the Stop hook's
`_failed_set` normalisation exists for, and it does not go away.

## Out of scope

Not the ordering defect fixed alongside this row's filing — `sort_by` in the
watcher's checks query, and `_failed_set` in the Stop hook. That is a different
mechanism (order, not ambiguity) and the two are independent: sorting makes the
rendering canonical and leaves it exactly as unparseable.
