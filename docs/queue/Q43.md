# A relaunched watcher re-fires a failure the session already declined

The watcher has two answers for a failing check and needs a third. Wake the
session — `scripts/pr-sentinel-watch.sh:547:emit_check_failure() {` — which
exits, so the Stop hook then wants a relaunch. Or wait, which is
`scripts/pr-sentinel-watch.sh:584:notice_base_failure() {`: non-terminal, the
watch continues, and the Stop hook sees a live watcher and stays quiet. The
dispatch between them is one line,
`scripts/pr-sentinel-watch.sh:1028:if (( BASE_CHECK == 1 )) && base_failures_only "$failed_links"; then`.

There is no third answer for a failure the session has already seen, judged not
its own, and been told to leave alone. A watcher process holds no memory across
runs, so every relaunch re-polls, finds the same red, and exits re-reporting it
within seconds. The session's only route to a quiet turn end is one it is not
going to take: push a fix.

## What was observed

One batch, measured 2026-09-09 in `actions-gateway/github-actions-gateway` from
the session transcript and the GitHub run data. A session opened four
documentation pull requests. Two of them, #1884 and #1893, were red on
`security-scan.yml` — a trivy image scan reporting CVE-2026-84445 in
`google.golang.org/grpc`. Neither branch touched Go: #1884's changed files are a
`Makefile`, four backlog rows and three docs pages. The maintainer was asked what
to do and said to ignore it and keep opening documentation PRs, so no push to
either branch was ever coming.

Every watcher launch for those two, with the two healthy PRs in the same batch as
controls:

| PR | launches | time to exit |
|---|---|---|
| 1884 | 16:58:37 | 2m53s — the first report |
| 1884 | 17:22:56, 17:23:44, 17:24:49 | 5s, 6s, 5s — same event, same head SHA |
| 1893 | 17:22:58, 17:23:45, 17:24:50 | 6s, 5s, 6s — same event, same head SHA |
| 1888 | 17:22:57 | 35s, `ready` |
| 1894 | 17:23:00 | 16m11s, a real watch |

Seven wake-ups across the two PRs. Five of them repeated a report the session
had already been given, on a state that by definition could not move: the head
SHA cannot change without a push, and no push was coming.

## The Stop hook's dampening is not the defect, and the report of it was wrong

The chip that opened this row said the dampening did not hold. It did. The hook
blocked twice — the harness's own record of both sits at transcript lines 958
and 1001 — and on the third stop emitted the non-blocking warning instead, as
`scripts/pr_sentinel_stop_hook.py:691:dampened = {}` and
`scripts/pr_sentinel_stop_hook.py:693:repeated = next((sig[0] for sig, runs in sig_launches.get(pr, {}).items()`
provide for. Replaying `_analyze` over the finished transcript returns
`{'1893': 'check_failure', '1884': 'check_failure'}` and an empty block set,
under the installed v0.9.0 copy and under `main` alike.

Two things made a working mechanism read as a broken one, and both are worth
keeping when the third answer is designed.

**Dampening is silent until it fires.** It lives in the Stop hook, which speaks
only at a turn end, so a session cannot know a relaunch is unnecessary until it
has already made one. The third relaunch above was made to satisfy a hook that
was no longer going to block —
`scripts/pr_sentinel_stop_hook.py:165:BLOCK_MARKER = 'pr-sentinel: you are ending your turn'`
is the last thing the session had been told.

**Dampening bounds the block and not the wake-up.** The watcher is the thing
that keeps re-firing, and it has never been told anything. Every relaunch above
was a fresh process with no knowledge of the reports before it.

## Why the base check did not cover this

`base_failures_only` is the instrument for exactly this failure class, it is on
by default, and it correctly answered "not inherited". The base branch's latest
completed run of `security-scan.yml` was green. It was also 18 hours old and
predated the vulnerability feed entry that turned the scan red. That is its own
defect, filed as Q44, which owns nothing of the measurement above — this row
does.

Q44 is the narrower fix and it does not retire this one. A check can be red on
a PR and not that PR's to fix for reasons no comparison against the base can
reach: a flaky job, an outage at a registry, a required check the maintainer has
decided to waive. The third answer is what covers the class; Q44 covers one
member of it.

## Two shapes

Both make an acknowledged failure non-terminal, so the watcher keeps polling and
the Stop hook sees a live watcher — no Stop hook change either way.

**Per-launch acknowledgement.** The relaunch carries the head SHA the session
accepts, and a `check_failure` at that exact SHA becomes a notice rather than an
exit. Opt-in, so no default moves, and the acknowledgement expires by itself the
moment anyone pushes. Cost: it is a new knob on the launch line, and Q35 has to
land first — the guard's auto-allow reads a three-token launch and an
env-prefixed or flagged one is not that, so the launch would prompt and the
duplicate-watcher deny would stop seeing it.

**Watcher-side dampening.** The watcher records its own last report and, on
finding the identical `(event, head SHA, failed set)` a relaunch later, notices
rather than exits. Needs no knob, needs nothing of Q35, and reuses the signature
the Stop hook already computes. Two costs: cross-run state is a new local write
and so a new `PRIVACY.md` disclosure, and this changes the default, which is the
thing `CLAUDE.md` reserves — a watcher that stops re-reporting on its own can
swallow a failure a session would have fixed had it been told again.

**Ask:** which of the two, and specifically whether the watcher may stop
re-reporting a failure by default. The security posture is not in question —
neither shape reads a comment, a PR body, or merges anything — but "secure by
default, not opt-in" and "when in doubt, add friction" put the default-loosening
half of this call with the maintainer rather than with a grooming pass. The
repo's own precedent points at the automatic shape: the Stop hook chose it for
this problem, on this signature. That precedent is about a hook that blocks a
turn, not about one that decides whether a session hears about a red check at
all, which is why it is offered here and not taken.
