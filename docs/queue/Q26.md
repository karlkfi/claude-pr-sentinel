# Let the overlap check recognise a stacked pull request

The `gh pr create` overlap deny has no notion of a branch deliberately built on
another open PR. A stack's diff against the base contains its parent's hunks by
construction, so the check fires on every stacked create — correctly by its own
rules, and on the one case that is not the duplicate-PR mistake it exists to
catch. Today the only way through is `PR_SENTINEL_OVERRIDE=<reason>`, which is
per-invocation by design, so a three-PR stack reaches for the escape hatch three
times and each one reads in the report like a suppressed warning.

Measured 2026-08-19 opening Q19 on a branch stacked on Q13's (#97): the two PRs
share `tests/test_watcher.py` and `PRIVACY.md` because the second reuses a
helper the first adds.

Cheapest shape: when the branch's merge-base with the candidate PR's head is the
candidate's head — i.e. this branch contains that PR — report a stack rather
than an overlap, and let the create through with a note naming the parent.
`git merge-base --is-ancestor <pr-head> HEAD` answers it in one call, and the
check already resolves both refs.

Q15 counts override use but does not remove the reason to reach for it.

Whoever implements this should add the caveat to README's guard-decisions
bullet in the same PR: the activity report's override count falls both when
sessions stop reaching for the hatch and when the guard stops firing where it
should not have, and this row is the second case. #98 deliberately left that
sentence out of the README because it is not true until this lands — so it
lands here, atomically with the behaviour that makes it true.
