# Attribute the guard overrides to a deny branch

The `hook-verdict` skill measured post-deny behaviour across six installed guard
plugins on one workstation (888 transcripts, 2026-08-21) and found pr-sentinel
with the **highest override rate of the six**: 25% of calls following one of its
denies carried an override variable, against prod-guard's 14% and
exit-status-guard's 0%. Its reading of that spread is that override use "rises
exactly where a rewrite is unavailable" — a deny carrying a runnable fix gets
complied with, and a deny that only states a principle gets routed around.

pr-sentinel denies on three branches, and they do not offer equally good
rewrites:

- the **poll deny** names the exact background launch to run instead, which is
  the strong shape;
- the **duplicate deny** names the `TaskStop` call that stops the incumbent
  watcher, which is also concrete;
- the **overlap deny** names the other PR and the shared paths, and there is no
  command that resolves it — deciding whether two branches should be one is
  the kind of judgement the skill says has no mechanical rewrite.

So a plausible reading is that the 25% is the overlap deny and is *correct*, the
case the skill's own "where the rule stops" carve-out describes. The point of
this item is that nothing here can tell that from the alternative, where one
branch's remediation is simply weak.

The report cannot answer it today, and says so at
`scripts/friction-report.py:206:# The escape hatch leaves no decision record`: an
override makes the guard defer, a defer is silence, so overrides are counted off
the command string rather than off any verdict. The count is a total with no
branch attached.

## What would settle it

Classify each counted override by which branch *would* have fired had the prefix
been absent — the guard's own classifiers (`classify_poll`, `is_pr_create`,
`watcher_launch_pr`) already decide this and are importable, so the report can
re-run them over the recorded command with the prefix stripped. That turns one
number into three and says which deny is being routed around.

Then act on the split rather than on the total. An overlap deny at 25% is the
system working; a poll deny at 25% means the fix-it is not being applied and the
remediation text is the thing to change.

## Not this

Do not add an `ask` verdict anywhere to "check" an override. `hook-verdict`'s
routing test puts every one of these branches on `deny`, and an approved ask
teaches the session nothing because it never reaches the model.
