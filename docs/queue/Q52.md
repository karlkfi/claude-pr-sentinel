# A SIGTERMed watcher child exits 143 and the suite reads it as a failure

Under concurrent load a watcher run can come back with exit status 143 and no
exception anywhere. `run_watcher` returns it as an ordinary return code, the
test asserts it against 0, and the suite reports:

```
FAIL: test_requeue_resets_the_dequeue_streak (test_watcher.WatcherCase)
  File "tests/test_watcher.py", line 1305, in test_requeue_resets_the_dequeue_streak
    self.assertEqual(rc, 0)
AssertionError: 143 != 0
```

Nothing is swallowed, nothing raises, and the assertion is correct. 143 is
128+15 — a process that died on SIGTERM — so the verdict reads as "the watcher
was killed", i.e. a defect in the code under test, when the run simply could not
be measured.

## Why this is not Q27 or Q48

Both of those record an **exception**. This is an honest exit status, which is
why it survives every instrument aimed at the other two:

| row | signature | how it surfaces |
|---|---|---|
| Q27 | `subprocess.TimeoutExpired` | the outer `run_watcher` cap expires and raises |
| Q48 | `JSONDecodeError` | a probe times out, `capture` returns `(None, '')`, the guard is silent |
| this | `AssertionError: 143 != 0` | a child dies on SIGTERM, bash exits 143, the assertion is right |

## The mechanism, measured

`scripts/pr-sentinel-watch.sh:57:set -euo pipefail` is what converts a dead
child into the script's own status. With `errexit` set, a foreground child
killed by a signal ends the script with that child's 128+N. Driven on a scratch
script whose only statement was `sleep 30`, SIGTERMing the `sleep` and leaving
the parent alone: the script returned **143**.

Two readings that look obvious and are both wrong, recorded because the second
one was written into a peer session's escalation before it was checked:

- **It is not `run_watcher`'s own cap firing.** That cap
  (`tests/test_watcher.py:184:    def run_watcher(self, files, pr="123", env=None, timeout=20,`)
  is `subprocess.run(timeout=)`, which **raises** `TimeoutExpired` — measured
  directly, `subprocess.run(["bash","-c","sleep 30"], timeout=1)` raises rather
  than returning anything. That path is Q27's, and it did fire separately in the
  same run.
- **It is not Python killing the process.** Python reports a child that died on
  a signal as a **negative** returncode — measured, a SIGTERMed bash comes back
  as `-15`, not `143`. A positive 143 can only be a status bash itself returned,
  so the signal reached a *child of the watcher* (a `sleep`, a `gh`, a `date`)
  and `errexit` propagated it.

## What is not established

Two separate questions, and the cheaper one is not the one that suggests itself.

**Which child receives the signal.** Unmeasured. The failing test passes no
`virtual_clock`
(`tests/test_watcher.py:1304:        rc, out, _ = self.run_watcher(files, env={"PR_SENTINEL_TIMEOUT": "4"})`),
so a real `sleep` is in the process tree — but that is a reading of the harness,
not an observation of the kill, and `gh` and `date` are in the tree too. A shim
in place of each watcher child, logging its own pid and the signal it dies of,
settles this without having to catch anything in the act.

**Who sends it.** Harder, and nothing here answers it. The run was on a
workstation with 75 peer sessions live, several building concurrently, so memory
pressure is a candidate and so is any supervisor that reaps a process group.

Take the recipient first: it bounds the search for the sender, and it is the one
a shim can close on its own. Do not write a cause into the fix without measuring
one.

## Why the in-flight work will not catch it

Q28's fix wraps `capture()` in `scripts/pr_sentinel_overlap.py` and keys on a
`TIMED_OUT` sentinel. That reaches every probe in `tests/test_overlap.py` and
nothing in `tests/test_watcher.py`, which never calls `capture` — so this
signature survives Q28 and Q48 both landing. Worth knowing before Q27 is
unheld, since Q27 is the row that owns `test_watcher.py`.

## What a fix looks like

`run_watcher` is the one place every watcher run passes through, so it can tell
an unmeasurable run from a verdict without touching a single test: treat a
return code above 128 as "could not measure" and raise or skip, rather than
handing it back as a value to assert on. The same reasoning Q48 applies to a
fail-open — the defect is that the harness cannot tell the two apart, not that
the watcher behaved wrongly.

Whether that belongs here or folded into Q27's fix is a scoping call for
whoever takes Q27; this row exists so the signature is written down somewhere
other than two session transcripts.

## Provenance

Measured 2026-09-18 on `ea81805` while working Q35 (PR #137, a diff touching
neither `test_watcher.py` nor `test_overlap.py`). One `make check` failed with 8
failures and 1 error; re-running the same tree was green. Both signatures
appeared in that one run — this 143, and a `TimeoutExpired` from
`test_a_late_run_clears_the_clock_rather_than_shortening_the_wait`.

Suite wall-clock, identical tree and identical 526 tests: **593.073s** on the
failing run against **316.660s** on the green one, 1.87x. Wall-clock is a
property of the host and cannot attribute a particular failure to a particular
probe; it is a banner for "this run could not measure", not a discriminator.

Peer-reported, not measured here — two sessions hit the same class on their own
trees the same morning, at 530/241 and 606.888/321.212. **Neither recorded a
143**, and their failure sets differ from this one's and from each other's: one
split 5 errors / 5 failures across both `test_overlap` arms, this run had 6
`test_overlap` failures plus the 143. Which probe loses the race looks
arbitrary, so treat any single run's failure set as a sample rather than as the
signature.
