# The watcher records one event for dampening; the Stop hook dampens five

Two dampeners disagree about which terminal events a repeat should quiet.

The Stop hook's `scripts/pr_sentinel_stop_hook.py:171:    r'PR-SENTINEL EVENT:\s*(check_failure|conflict|behind|dequeued|base_fixed)(?![\w-])')`
names five, and its own comment explains why the heal events belong there: the
session has usually already done the work and is waiting on its gate, so the
remote head cannot have moved yet.

The watcher writes a record for one. `scripts/pr-sentinel-watch.sh:711:record_report() {`
has a single call site, `scripts/pr-sentinel-watch.sh:1450:					record_report check_failure "$failed_names"`,
so `conflict`, `behind`, `dequeued` and `base_fixed` are never recorded and a
relaunch can never recognise one as already reported.

The consequence is an asymmetry rather than a silence. A session that receives
`behind`, decides to defer the rebase, and relaunches the watcher gets woken
again at the same head — every time. The Stop hook stops *blocking* on it,
because that side does dampen; the wake itself repeats. So the two mechanisms
half-cancel: the backstop goes quiet and the interruption does not.

## What was measured

2026-09-18, on the branch adding `base_fixed`.

```
stop hook DAMPENABLE_EVENT_RE  check_failure conflict behind dequeued base_fixed
watcher   record_report        check_failure
```

Three of the four gaps predate that branch. On `main` at `b3334a4` the regex
named four events and `record_report check_failure` was already the only call
site — so `conflict`, `behind` and `dequeued` have had this since the dampening
landed, and `base_fixed` inherited it by being written the same way.

## Why it was written that way

The reasoning recorded at the `base_fixed` dispatch was that a heal
instruction is cheap and an unmoved head proves it was not carried out. The
first half is true and the second is the trap: an unmoved head does establish
that no push happened, and says nothing about whether the session *decided*.
Deferring a rebase is a legitimate stance — a branch stacked on a parent that
has not merged, or a session still running its gate — and those are exactly the
cases the Stop hook's own comment cites as the reason to dampen.

## Proposal

One candidate, not a prescription. Record every event the Stop hook considers
dampenable, so the two agree by construction rather than by two lists staying
in step: pass the event name to `record_report` at each terminal heal emit, and
give the heal events the `repeat_*` treatment `check_failure` has.

Worth weighing against it: `check_failure` earned its notice because the
dampened case is common and the report is long (a CI log excerpt rides with it).
A repeated `behind` is four lines. The cost of the repeat is smaller, so the
value of suppressing it is smaller, and four near-identical notice emitters is
real surface. A cheaper shape is one notice that names the event it is
declining to repeat, rather than one per event.

Worth recording as a non-fix: narrowing the Stop hook's regex to match the
watcher would make the two agree and is the wrong direction — it would restore
the block on a repeat that nobody can act on, which is the livelock the
dampening exists to prevent.

## Why this ranks here

Not a correctness defect: nothing is mis-attributed and nothing fails open. It
is an interruption the design already decided was not worth making, applied to
one event out of five. It is cheap to close and it has been quietly true for
three events long enough that nobody has reported it, which is also the reason
not to rush it into a release.
