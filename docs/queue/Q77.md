# A planned sibling overlap escapes only by an override auto mode refuses

The overlap check denies a `gh pr create` whose branch collides with an open
PR. That is the right call for a session that did not know the other PR
existed. It is the wrong call for a session coordinating a batch, which split
one item into parallel PRs knowing they would conflict and planned to merge
them in sequence. Today the only way past the deny for that case is the
inline `PR_SENTINEL_OVERRIDE=<reason>` prefix, and Claude Code's auto-mode
classifier refuses that prefix as a safety bypass. So every worker in an
overlapping batch costs Karl a hand approval.

## What was measured

2026-11-10, in `actions-gateway/github-actions-gateway`, on installed
pr-sentinel 0.12.0. A coordinating session split that repo's backlog row
Q1322 into four PRs, #2294 to #2297, that each edited the same four docs:
`docs/operations/upgrade.md`, `docs/releases/v2.0.0.md`,
`docs/queue/Q1322.md` and `docs/plan/security-audit-2026-11.md`. A pairwise
trial merge showed all six pairs conflicting textually, in docs only. #2294
opened first. The overlap check then denied the create in each of the other
three worker sessions, naming #2294 first, for example (09:49:09Z):

> pr-sentinel: refusing `gh pr create` — this branch edits lines an open PR
> already changes: #2294 (docs/operations/upgrade.md,
> docs/plan/security-audit-2026-11.md, docs/queue/Q1322.md,
> docs/releases/v2.0.0.md); […]
> If the overlap is known and deliberate, re-run with an inline
> PR_SENTINEL_OVERRIDE=<reason> prefix on the command itself […]

Two of the three sessions retried with the prefix unprompted, and the
classifier refused it, three times across those two sessions:

> Permission for this action was denied by the Claude Code auto mode
> classifier. Reason: [Safety Bypass Flag].

The third session never retried before Karl stepped in. All three creates
then went through inside four seconds of each other (10:28:20Z to 10:28:23Z)
after Karl approved the override by hand, opening #2295, #2296 and #2297. One
override reason reads "approved by Karl for this create". The transcripts are
the worker sessions under
`~/.claude/projects/-Users-karl-workspace-github-actions-gateway--claude-worktrees-{quirky-franklin-08fa21,magical-jemison-785781,vigilant-ritchie-fcb64b}/`.

Neither unreleased overlap fix helps. Q68 (#176, trial merge decides a
suspected overlap) can at best confirm this collision, since these branches
really do conflict. Whether it trial-merged here at all depends on the
sibling's head being local, which was not checked.
Q69 (#179, never deny on a shared path alone) drops the path-only entries
#2291, #2283 and #2084 from these denies, but #2294 stays.

## Why the existing escape does not reach it

#178 already lets a create through over a PR it says it replaces: a
`--title` or `--body` containing `Supersedes #N` takes #N out of the count
(`scripts/pr_sentinel_guard.py:376:def pr_create_replaced(command, lenient=False):`).
That works because the word has a cost. The reviewer reads it and closes #N.
A sibling is not replaced, so writing "Supersedes" would be false and would
get a live PR closed.

All three workers also passed their body as `--body-file`, which that escape
never reads:
`scripts/pr_sentinel_overlap.py:625:        f'not counted. A --body-file is not read. The reviewer will close #{first} '`.
The Q62 report text recommends `--body-file` too, so body text alone would
not have reached these creates even with the right word in it.

## Candidate shape, to weigh rather than assume

A create whose own text names the conflicting open PR as a known sibling —
"Sibling of #2294", or "conflicts with #2294 by design" — gets an overlap
**report** for that PR instead of a deny, the way Q62 reports a create it
cannot parse strictly. Every open PR the create does not name still denies.
The cost is the same kind #178 relies on: the claim sits in the PR body the
reviewer reads, and it tells the reviewer to sequence the merges.

That shape lets through something the check catches today. The deny itself
names #N, so a session that never knew about #N, and is duplicating its work
by accident, learns the number from the refusal and can add "Sibling of #N"
and re-run. "Supersedes" has the same hole but carries a penalty, since the
reviewer closes #N. "Sibling" has none. In practice that turns the deny into
a speed bump the model clears alone, and the reviewer becomes the only
backstop. The report would still name #N and its paths, and the PR body
would say so, so the accident stays visible in review, but it is no longer
stopped before review.

**Ask:** whether reviewer-visible disclosure is an acceptable price for
letting a create past its own deny. It loosens a security default, which
`CLAUDE.md` puts behind Karl's sign-off. The questions under it:

- The deny teaches the number. If disclosure is not enough, the sibling
  word needs evidence the session cannot get from the deny. One candidate:
  both PRs name the same backlog item in their branch's commits. That evidence is author-written
  text read off git, and the open PR's `title` stays off limits under the
  `gh --json` field rule.
- Should the check read `--body-file`? That is a new local file read, so it
  needs a `PRIVACY.md` entry, but without it the escape misses how workers in
  this kind of batch actually write their bodies. Title-only is the narrow
  alternative.
- Report, or allow silently? A report keeps the collision in the session's
  context, which matters when the sibling merges first and this one goes
  `CONFLICTING`.

Done is the chosen shape, a test in `tests/test_overlap.py` that replays the
Q1322 case (a create naming its conflicting sibling is reported, a create
naming nothing still denies), and updated README PreToolUse rows and deny
text.
