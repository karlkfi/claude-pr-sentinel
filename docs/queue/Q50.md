# The PRIVACY disclosure gates see reads and are blind to writes

Four gates ask what a component **reads** and none asks what it **writes**.
`tests/test_watcher.py:2122:def undisclosed_reads(script, privacy):` takes the
GraphQL surface,
`tests/test_watcher.py:2147:def undisclosed_rest_reads(script, privacy):` the
`gh api` paths,
`tests/test_watcher.py:2341:def undisclosed_globs(script, privacy):` the file
patterns a Python component opens, and
`tests/test_watcher.py:2330:def undisclosed_components(privacy):` the sections
themselves. A component that starts writing to disk trips none of them.

`CLAUDE.md:105:**Disclose every read.** A new GitHub read, a new local file read, or a new`
enumerates the same three things and says the disclosure tests fail the build
otherwise. For a write that sentence is true of the obligation and false of the
enforcement.

## What was measured

2026-09-18, on the branch that gave the watcher its first disk write — the
cross-run record behind the relaunch dampening. The two disclosing bullets were
deleted from `PRIVACY.md`'s watcher section, leaving the code as shipped, and:

```
python3 -m unittest tests.test_watcher.PrivacyDisclosure \
                    tests.test_watcher.PrivacyComponents
Ran 8 tests in 0.025s
OK
```

Eight cases, all green, exit 0, against a script that writes a file the policy
no longer mentioned. The disclosure rode on someone remembering — which is the
same thing the merge-queue actor read did before
`undisclosed_reads` existed, and the same thing Q12's REST read did before
`undisclosed_rest_reads` did.

Two stale sentences were in the tree at that moment, both repaired in that
branch and neither found by a gate: the watcher section's "It writes nothing to
disk", and the migration helper's claim to be "the only component that does".
The second is the one worth noting — it was falsified from a **different**
component's section, so even a per-component write gate would have to compare
across sections to catch it.

## What is already covered

`tests/test_watcher.py:2180:def undisclosed_writes(script, privacy):` was added
on that same branch and closes the narrow case: the watcher holds a write knob,
so its section must name `PR_SENTINEL_STATE_DIR` and must not still say it
writes nothing. It ships both can-fail arms and an arm proving it stays quiet on
a component that really writes nothing.

That is deliberately one component and one knob. It does not generalise, and it
would not have caught the migration-helper sentence.

## Proposal

One candidate, not a prescription, and the honest position is that the gate's
reach is limited by what a bash redirect looks like.

Detecting a write in the shell is the hard half — every target in the watcher is
a variable assembled from two more, which is why the existing check asks about
the knob instead. The tractable version is the **cross-section** one, which needs
no shell parsing: no section may claim a component "writes nothing to disk" while
that component's own script holds a write, and no section may claim to be the
only one that writes while more than one does. Both are string questions over
`PRIVACY.md` plus a per-component predicate, and the second is the exclusivity
claim nothing can currently check.

The Python components are the easier population — an `open(..., "w")`, a
`Path.write_text`, a `shutil` call are all greppable in a way a redirect is not,
so a write gate that covers the four Python scripts and leaves the bash watcher
to its knob check is worth more than nothing and is most of the surface.

Worth recording as a non-fix: raising this to the PR template's self-attested
checkbox is where the read gates started, and the checkbox is what failed at
v0.9.0. The reason those gates exist is that CI asks the question instead.

## Why this ranks low

The plugin has exactly one disk write today, it is disclosed, and it is gated by
the narrow check above. The gap is real and it bites on the *next* write, in
whichever component acquires one — so it is a trap laid for a future change
rather than a defect anybody is currently paying for.
