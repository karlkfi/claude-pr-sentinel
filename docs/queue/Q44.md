# A stale-green base run reads as a green base

`base_run_failure` asks GitHub for the base branch's newest **completed** run of
one workflow and reads its conclusion —
`scripts/pr-sentinel-watch.sh:406:base_run_failure() {`, querying
`branch=${BASE}&status=completed&per_page=1`. Green there means the failure is
this PR's own, and the session is woken to fix it.

That is a claim about a run, used to answer a question about code. The two come
apart whenever a check's verdict depends on something outside the repository —
a vulnerability feed, a licence database, an upstream API, a moving `:latest`
base image. The base's last run passed against yesterday's inputs; the PR's run
failed against today's. Nothing about the branch changed, and no comparison of
run conclusions can see that.

## What was measured

2026-09-09, `actions-gateway/github-actions-gateway`, pull request #1884 — a
documentation change touching a `Makefile`, four backlog rows and three docs
pages, and no Go at all. Its `security-scan.yml` run 34380057963 failed at
16:58:36Z on CVE-2026-84445 in `google.golang.org/grpc`.

The base branch's six newest completed runs of that same workflow were all
`success`, the newest being run 34287302603 at 2026-09-08T22:43:16Z — 18 hours
before the PR's run, and the last time the workflow had run on `main` at all.
The dependency was `main`'s, the branch could not have introduced it, and the
comparison still answered "not inherited" because the only two data points it
had were a green run and a red one.

`emit_check_failure` then told the session to diagnose and fix it
(`scripts/pr-sentinel-watch.sh:555:Next action: diagnose and fix the failing check(s) below in this local`),
and said nothing about the base comparison having happened, so nothing in the
report showed the verdict resting on a stale green.

## This is Q38's shape, one step further out

Q38 records a base that has gone green while a head that predates the fix keeps
failing — decidable, because ancestry is readable. This one is not decidable
from run data at any price: establishing that the base is red *today* means
running the base's workflow today, and a watcher that triggers workflow runs is
not something this plugin should become.

Q43 owns the measurement of the session cost this produced and carries the
general escape. Neither row retires the other: the escape covers any failure a
session declines, and this row is about the report being honest when the
instrument is the reason it woke.

## Proposal

One candidate, and the honest position is that the wake is correct — waking on
an unknown is the fail-safe direction, and every alternative that "treats an old
run as unknown" resolves to waking too. What is wrong is the report.

Have `emit_check_failure` state the base comparison it made, when `BASE_CHECK`
is on and a base run was resolved: the workflow file, the run id, its conclusion,
and how old it is. `notice_base_failure` already prints that shape for the
inherited case, so the data is assembled and only the green branch discards it.
A session reading "the base's last run of `security-scan.yml` was green 18 hours
ago" can weigh it in a way it cannot weigh silence — and where the check reads an
external feed, that line is the whole finding.

Two smaller things fall out of the same edit. A base with no run of the workflow
at all currently reads identically to a base with a green one, both routed by
`scripts/pr-sentinel-watch.sh:1028:if (( BASE_CHECK == 1 )) && base_failures_only "$failed_links"; then`;
naming which of the two it was costs a line. And `base_failures_only` is
all-or-nothing, so a mixed set wakes with no indication that some of its members
were inherited — the detail it already builds in `BASE_FAIL_DETAIL` is thrown
away on that path.
