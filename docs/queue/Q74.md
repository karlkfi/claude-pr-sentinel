# An UNSTABLE `ready` could name the checks it absorbed as advisory

On `UNSTABLE`, `ready` and `ready_watching` name two possible causes and refuse
to pick: an advisory check failing, or a run that registered after the rows
were read (`scripts/pr-sentinel-watch.sh:1342:		echo "  - a non-required or advisory check is failing — e.g. a"`).
On one route the watcher does know which it is. When `failures_absorbed`
counts a `continue-on-error` failure as passing, the poll already holds the
absorbed checks' names, and it sends them only to stderr
(`scripts/pr-sentinel-watch.sh:1752:				warn "failing checks absorbed by continue-on-error (workflow run concluded success): ${failed_names}"`),
which the session never reads.

So where absorption happened on the polls that confirmed green, the report
could say "absorbed as advisory: <names>" and leave the refuse-to-pick wording
to the case it was written for: no absorption, and the disagreement is
unexplained.

Raised as a note in review of the Q36 change, not as a hold.

## Open question for the implementer

`ready` fires `PR_SENTINEL_GREEN_POLLS` polls after the first green one, and
absorption is decided per poll, so the names have to survive across those
polls. They also have to be cleared on any poll that absorbs nothing, or a set
from an earlier head is reported against a later one. Nothing about that is
measured yet. Check names come from workflow files a fork's PR can edit, so
read `CLAUDE.md`'s field rules before echoing them into a report: the
`Failed checks:` line already prints them, which is the precedent.

## Why this ranks here

Better wording on a report that is no longer wrong. Q36 already stopped it
calling an UNSTABLE PR green, so this is a precision gain, not a fix.
