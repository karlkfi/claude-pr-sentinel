# A push after then, do or { is never classified

The PostToolUse hook classifies each simple command by its first word, and the
shared tokenizer splits only on operators, so a shell reserved word stays glued
to the front of the command it introduces. `if true; then git push origin feat;
fi` reaches `classify_command` as `['then', 'git', 'push', 'origin', 'feat']`,
whose first word is `then`, not `git`, and the push is never seen. The PR it
updated goes unwatched, which is the failure this plugin exists to prevent, and
nothing records that a nudge was missed.

Measured 2026-11-10 against `origin/main` at `bcd84c5` by driving
`detect_action` with a working directory whose `origin` is a forge:

| Command | Classified |
|---|---|
| `git push origin feat` (control) | `git_push` |
| `if true; then git push origin feat; fi` | `None` |
| `for b in a; do git push origin $b; done` | `None` |
| `while true; do git push origin feat; break; done` | `None` |
| `{ git push origin feat; }` | `None` |
| `! git push origin feat` | `None` |
| `time git push origin feat` | `None` |

Found in review of #183 (Q51), which tracks `cd` across simple commands. The
same glue hides a `cd` after a reserved word from that tracking, as in `if cd
../x; then git push …`, so a fix here should strip the prefix in one place that
both `classify_command` and `_after_cd` read.

The guard (`scripts/pr_sentinel_guard.py`) classifies on the same tokenizer and
may miss a foreground poll behind `then` the same way. That is unmeasured.

Cited: `scripts/pr_sentinel_hook.py:101:def _strip_env_prefix(argv):`
