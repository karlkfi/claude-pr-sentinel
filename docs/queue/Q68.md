# The overlap deny refuses PRs that git merges cleanly

The overlap check denies `gh pr create` when this branch's edits come within
six lines of an open PR's (`CONTEXT_LINES` either side, in
`scripts/pr_sentinel_overlap.py`). Git conflicts only when the changed regions
actually touch. Two branches adding neighbouring rows to one doc table are
therefore refused here and merge cleanly everywhere else, and the deny's two
remedies — fold this branch into that one, or narrow it — fit neither.

What the refusal then costs is a human prompt. The deny names an inline
`PR_SENTINEL_OVERRIDE=<reason>` prefix, which is meant to be model-settable,
and Claude Code's auto-mode classifier refuses that prefix as a safety bypass.
So the override tier this check was designed around does not exist in auto
mode, and every false positive reaches Karl.

## Measured

2026-11-01, installed pr-sentinel 0.12.0, one parallel dispatch of eight
worker sessions in a repo whose merge queue already arbitrates conflicts. Two
of the eight creates were denied, both over shared operations docs:

| create | denied over | worker's own reading |
|---|---|---|
| PR A | 2 open PRs by range, 1 by shared path only | additive rows beside theirs |
| PR B | 3 open PRs by range, 1 by shared path only | "trial merges clean" vs the 3 |

Both workers then retried with an override reason, and both retries came back
`Permission for this action was denied by the Claude Code auto mode
classifier. Reason: [Safety Bypass Flag]`. Each create went through about two
hours later, once Karl approved the same command in a prompt. Both PRs merged
after an ordinary rebase.

PR B's claim was re-checked by `git merge-tree --write-tree`, git 2.55.0, at
the head SHAs read off each PR's timeline for the time of the create: **clean
(exit 0)** against two of the three range hits. The third had been
force-pushed since and its create-time head was not recovered; PR A's
create-time head was not recovered either, so PR A is unmeasured.

The path-only hit (an older PR, the same one both times) conflicted, exit 1 —
but on the same five files it also conflicts on against PR B's own merge base.
That PR was stale against the default branch, and PR B added no conflict of its
own. A naive trial merge would still have denied on it.

## Shape of the fix

Deny on a trial merge rather than on proximity. For each open PR that shares a
path: `git merge-tree --write-tree --name-only` of this branch's tip against
the PR's head, and of this branch's fork point against the same head; deny
only on the conflicted paths the first has and the second lacks — the conflicts
this branch introduces. The range comparison stays as the cheap pre-filter it
already is, and as the fallback wherever the trial merge cannot run.

What this needs that the check does not do today:

- **The PR's head as a local object.** `gh pr diff` returns text, not
  commits. A worktree of the same clone often has the branch already
  (`head_ref` resolves `refs/remotes/origin/<head>`); a `git fetch` of the head
  SHA would be a new network call in a hook someone waits on, against the
  per-probe `PROBE_TIMEOUT`.
- **git 2.38+** for `merge-tree --write-tree`. An older git falls back to the
  range result, not to allow — this branch's whole point is to deny less, not
  to fail open more.
- **No new GitHub read** if the head comes from local refs, so `PRIVACY.md`'s
  overlap section may need only the local git reads named.

## Not chosen

**Advisory wherever a merge queue exists.** Detecting one needs a rulesets or
branch-protection read — a new GitHub read to disclose — and a merge queue
catches conflicts, not the duplicated work this check also exists for. It
would also silence the check on exactly the repos running parallel dispatches,
which is where duplication happens.

**Flip the verdict to `ask`.** That is what the classifier already turns it
into, measured above; it spends Karl on every false positive.

## Open question

Whether a clean trial merge should be silent or still emit an advisory naming
the neighbouring PR. Silence is what removes the friction; an advisory keeps
the duplicated-work signal for two branches that rewrote one function in
non-touching hunks, which a clean merge does not rule out.
