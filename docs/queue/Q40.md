# The Stop hook sees only its own watcher, so a foreign one still blocks

The Stop hook's block asks "is a watcher tracking this PR", but the only
watcher it can see is this plugin's own. `WATCH_ARG_RE` at
`scripts/pr_sentinel_watchers.py:27:WATCH_ARG_RE = re.compile(r'pr-sentinel-watch\.sh["\']?\s+(\S+)')`
matches one basename, `live` at
`scripts/pr_sentinel_stop_hook.py:593:live = set(scan.live())` is built from
those matches alone, and
`scripts/pr_sentinel_stop_hook.py:602:block = owned - concluded - live`
subtracts nothing else. A session running a different PR watcher is told
"no watcher is tracking it and CI may still be running"
(`scripts/pr_sentinel_stop_hook.py:645`) and has to launch a second one.

Reported 2026-09-04 from `karlkfi/claude-bouncer` on pr-sentinel 0.9.0. A
session following the
[`session-orchestrator`](../development/skills.md#session-orchestrator) skill
opened a PR and armed that skill's `pr-mergeability-watch.py` against it, as
the skill's §7 requires; it says it confirmed the process live before the turn
ended. The Stop hook blocked anyway, and the session ended up with two watchers
polling one PR. The code above is what was verified here — the process check
is the reporter's.

## The overlap is partial, which is why this is not a one-line fix

The foreign watcher does not subsume this one. Its `gh pr view --json` field
list is `state`, `mergeStateStatus`, `baseRefName`, `headRefOid` — no
`statusCheckRollup` — and it exits on
`conflict`, `head_change`, `closed`, `timeout` or `error`, where `conflict`
means `mergeStateStatus` in (`DIRTY`, `BEHIND`). It therefore has no view of
check conclusions at all, and a check failure that moves nothing else — the
head is unchanged, the merge is not dirty — wakes nobody until the polling
budget runs out — a `--timeout` defaulting to 21600 seconds. The conflict half
of the hook's question is genuinely answered by that watch. The CI half is not.

So treating a foreign watcher as satisfying the block would silently drop the
coverage this plugin exists to provide.

## Two things worth having straight before designing

**The friction is one block per pull request, not one per turn.** The reporting
session read it as firing at every turn end, which would make a five-stream
batch cost ten blocks per turn. It does not: `REPEAT_ASK` dampening
(`scripts/pr_sentinel_stop_hook.py:614`, from #77 via #95) turns the second and
later stops on the same PR into a non-blocking notice. The cost of a ten-PR
batch is ten blocks over the whole run.

**Recognising a foreign watcher crosses no read boundary.** A launch is a
`run_in_background` Bash `tool_use` in the session's own transcript, which is
where this hook already reads every signal it has. Matching a different
basename in that same record adds no network call, no process-table read, no
new local file, and nothing from the PR comment channel. `PRIVACY.md` would
need no new source. The trust model is also unchanged in kind — the hook
already believes the transcript when it says this plugin's watcher was
launched. What *does* change with a loose matcher is how cheaply a session can
silence the backstop by backgrounding something watcher-shaped.

The only existing escape is `PR_SENTINEL_DISABLE=1`
(`scripts/pr_sentinel_stop_hook.py:711`), which turns the whole plugin off. There
is no per-PR or per-watcher opt-out.

## Two decisions, and this row is not making either

They are independent, and conflating them is the trap: what the hook *does*
about a foreign watcher is not the same question as what *counts* as one.

**What the verdict should be.** Allowing the stop outright is the one option to
reject — it drops the CI half silently, which is the coverage this plugin
exists for. That leaves downgrading the block to the existing non-blocking
notice, which reuses the `dampened` path already built for this shape and can
say in the notice that the foreign watch does not report CI failures; or
keeping the block and only naming the foreign watcher in its text, which is
today's behaviour plus an acknowledgement and still leaves two watchers.

**What counts as a foreign watcher.** A hardcoded allowlist of basenames is
narrowest and hardest to trip accidentally, but couples this plugin to one
skill's script name, helps nobody running anything else, and goes stale the way
Q22 and Q35's option 3 go stale. A documented `PR_SENTINEL_EXTRA_WATCHERS`
generalises and decouples, but moves the reconciliation onto whoever writes the
config and makes the backstop as silenceable as that value is careless. Neither
is spoof-proof — a session that wants to quiet the hook can name a file
whatever it likes — so the matcher's job is to not fire by accident, not to
resist a determined session.

**Doing nothing is a real option.** The block's text already offers prose
("if you have already handed this PR to a human for merge review, you may
stop") that the model has to act on and the hook cannot verify, so a documented
note is consistent with what is already there. It leaves the duplicate watcher.

Whichever wins, `tests/test_stop_hook.py` needs a transcript with a live
foreign watcher and no pr-sentinel one, and `tests/test_watchers.py` needs the
matcher's negative case — a backgrounded `gh pr view <PR>` must not read as a
watcher. A new env var also needs a README Configuration row, or
`test_every_env_var_is_in_the_configuration_table` fails.
