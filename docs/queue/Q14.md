# Don't nudge on a refspec-less push from the default branch

`classify_command` treats a `git push` as PR work unless a refspec says
otherwise, and a bare `git push` carries no refspec, so pushing from `main`
still asks the session to watch a branch that has no PR of its own. Q5 closed
the explicit-refspec half only.

## The decision is already made; this is the mechanism

This row was filed asking whether the behaviour *should* extend, and it should:
#82 (`326ab1f`) settled the rule as "the push is PR work only if some refspec
targets neither a tag nor the default branch", and a bare push resolving to the
default branch is that case with the refspec implied rather than written.

The objection the row carried — that it silences a fork whose `main` has a PR
upstream — is not new to this half. #82 already silences `git push origin main`
from such a fork, so the trade was accepted when the rule was written, and
declining here would leave the hook inconsistent about the same push depending
on whether the refspec was spelled out.

## What is actually left

Resolving what a bare push targets, locally and without hardcoding a name. It
reads `push.default`, then `branch.<current>.pushRemote` /
`branch.<current>.remote` / `remote.pushDefault` to find the remote, and
`branch.<current>.merge` for the target under `upstream`/`simple`. #82's own
fallback applies unchanged: where the answer cannot be read, nudge, as before.

The triangular case (`remote.pushDefault` differing from the fetch remote) is
the one worth a fixture, because it is where `simple` and `upstream` disagree
about what a bare push even means.
