# Check the claims namespace against history in CI

**Scoped 2026-09-18, re-measured against `b3334a4`. Most of this arrived on main through
#134 and what is left has no live path to fire, so it is deferred rather than
built or deleted.**

**Event:** the command under *Every ID ever spent holds a claim* in
[`maintaining-backlog.md`](../development/maintaining-backlog.md) returns a
non-empty left-hand difference — an ID history has spent that holds no claim.
That is the one condition the unbuilt half of this row would catch, and it is
one command to ask.

The row asked for a `comm` between history and `git ls-remote` in CI, with two
properties: fail closed on an unreadable remote, and read the left-hand list
rather than trust an empty result. #134 (2026-09-12, the vendored `queue.py`
refresh to claude-skills `46a4f18`) brought `_shipped_ids` in, and CI's
`backlog` job already runs `queue.py claims --strict` with `fetch-depth: 0`.
Between them all three properties exist:

- **The history read.** `_shipped_ids` walks
  `git log --full-history --no-renames --diff-filter=D` over the store, so an
  ID a branch adds that this repo already completed is refused at the gate.
- **Fail closed on an unreadable remote.** `disclose()` plus `--strict` makes
  an unreadable remote *or* an unreadable history fatal.
- **Not trusting an empty result** — and better than this row specified. It
  asks `git rev-parse --is-shallow-repository` first and refuses outright,
  rather than under-reporting from the graft point while looking complete.

## What is genuinely left

`_shipped_ids` keys on a **deletion under `docs/queue/`**, so it cannot see an
ID that never had a file there. That is exactly the Q17 shape this row was
filed about. Measured at `origin/main` = `b3334a4`, 2026-09-18:

| reading | result |
|---|---|
| IDs `_shipped_ids` can see | 23 — every row this repo has deleted; it grows with each completion |
| Q17 among them | **no** — `docs/queue/Q17.md` never existed, so no deletion of it does |
| Q17 claimed on the remote | yes (backfilled 2026-08-19) |
| spent / claimed / **unclaimed** | 53 / 55 / **0** — `--all` over this clone's
  ref set, so both totals move with what has been fetched and with every
  concurrent allocation; the **0** is the reading that matters |

So the legacy-table shape is covered by the claim alone, and by nothing else.
The converse this row names — *every* ID history has spent still holds a claim
— is still literally unimplemented.

It has no live path to fire. `docs/STATUS.md` is gone from main, so no new ID
can be spent that way; every ID now comes from `alloc-queue-id.sh`, which
claims before it returns; and `queue.py claims` demands a claim for every ID a
branch adds. Spending an unclaimed ID would take a hand-picked number, which
that same check refuses. The claims with no row are Q24 and Q55 — allocated,
never filed — the stranded-ID case the docs already call intended.

## The embedded question: should `highest_local` read `docs/STATUS.md` by default?

**No**, and the first reason settles it without reaching the merits:
`alloc-queue-id.sh` is vendored from the skill, so a local change to its
default is overwritten by the next refresh — #134 was exactly such a refresh.
Changing it is an upstream ask, not a change here.

On the merits it would also buy nothing. The floor is
`max(highest_local, highest_claimed)`, and `highest_claimed` reads the claims
namespace directly, so it dominates an under-reporting local floor. Driven
2026-09-18 against a throwaway remote — store holding only `Q1.md` (so
`highest_local` = 1) and Q2–Q30 claimed — the allocator returned **Q31** on the
first attempt.

That measurement also corrects this row's own stated mechanism. The row argued
an under-reporting floor "now exhausts `MAX_ATTEMPTS` and dies loudly instead
of reissuing a used ID". It does not exhaust anything: the floor never falls
below the highest claim, so the walk starts on a free ID and succeeds
immediately. The conclusion the row drew was right; the route it gave was not.
