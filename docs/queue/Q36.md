# `ready` can fire while GitHub still reports the checks re-running

`emit_ready` (`scripts/pr-sentinel-watch.sh:713:emit_ready() {`) echoes the
merge state and then prints a fixed summary that does not derive from it
(`scripts/pr-sentinel-watch.sh:718:conflict. Nothing left to`). When the state
is `UNSTABLE` the two lines contradict each other in the same report, and a
reader cannot tell which to believe. `notice_ready_watching` just below it has
the same shape.

`UNSTABLE` reaches there because the readiness guard is a denylist
(`scripts/pr-sentinel-watch.sh:1068:&& [[ "$MERGE" != "BLOCKED" && "$MERGE" != "UNKNOWN" ]]; then`)
and `UNSTABLE` is not on it. `green` comes from the `gh pr checks` buckets, a
different API call from the `gh pr view` that reads `mergeStateStatus`, so the
two can disagree across the window in which a workflow run is registering.
`PR_SENTINEL_GREEN_POLLS` narrows that window without closing it: a run that
registers between the checks read and the view read leaves the buckets empty
and the merge state `UNSTABLE`.

It is not only a confusing report. `emit_ready` is terminal — it exits 0 and
tells the session to hand back for merge review — so the watch ends on a head
whose checks may still be running. The trigger is ordinary rather than a race
nobody meets: observed 2026-08-24 in `karlkfi/claude-bouncer`, where a
`gh pr edit` on a PR body re-fired a workflow triggering on the `edited`
pull-request event, the watcher sampled inside that run's pending window, and
the report read `mergeStateStatus: UNSTABLE` above the fixed green summary. An
orchestrator that keeps PR bodies current hits this routinely.

Same family as #40 (`ready` fires on `UNKNOWN` — the guard is a denylist of
one), #37 and #29. `UNSTABLE` is the member still not on the denylist.

Two pieces, and they should not be bundled:

1. **Derive the summary from the state.** Cheap, no behaviour change: the
   report stops contradicting itself whatever the readiness rule decides.
2. **Decide whether `UNSTABLE` should withhold `ready`.** This is the open
   question, and it is narrower than it looks: the unconditional form is
   already rejected on record
   (`docs/DESIGN.md:466:repo can sit in them indefinitely.`), because
   `UNSTABLE` covers a non-required check failing, so an unconditional hold
   strands the watch until `timeout` on a PR that is genuinely ready to merge.
   What is undecided is whether it deserves a *transient* hold of the shape
   `BLOCKED` already has — N consecutive polls before firing, which covers the
   registering-run window without stranding anything — or nothing beyond the
   report fix in (1).
