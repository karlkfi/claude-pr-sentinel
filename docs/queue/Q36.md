# `ready`'s summary calls the PR green while its header says `UNSTABLE`

`emit_ready` (`scripts/pr-sentinel-watch.sh:1069:emit_ready() {`) echoes the
merge state and then prints a fixed summary that does not derive from it
(`scripts/pr-sentinel-watch.sh:1075:echo "All checks are green and the PR has no merge conflict. Nothing left to"`).
On an `UNSTABLE` PR the two contradict each other four lines apart and a reader
cannot tell which to believe. `notice_ready_watching` has the same shape
(`scripts/pr-sentinel-watch.sh:1092:echo "All checks are green and the PR has no merge conflict. Hand it back to a"`).

It is not only a confusing report. `emit_ready` is terminal — it exits 0 and
tells the session to hand back for merge review — so the watch ends on a head
GitHub is reporting a non-passing commit status for. `UNSTABLE` reaches there
because the readiness guard is a denylist
(`scripts/pr-sentinel-watch.sh:1529:&& [[ "$MERGE" != "BLOCKED" && "$MERGE" != "UNKNOWN" ]]; then`)
and `UNSTABLE` is not on it. Same family as #40 (`ready` fires on `UNKNOWN` —
the guard was a denylist of one), #37 and #29.

## Two routes reach green-and-`UNSTABLE`, and only one is a race

Re-derived 2026-09-19 at `65a9700`. Both halves correct the mechanism this row
was filed with.

**The durable route, which the watcher creates deliberately.** A failing check
whose workflow run still concluded `success` is folded into the pass count
(`scripts/pr-sentinel-watch.sh:1405:pass_count=$(( pass_count + fail_count ))`),
so `green` is 1. `docs/DESIGN.md` already names the other side of that state —
`UNSTABLE` is "a non-required check failing"
(`docs/DESIGN.md:559:ready. An allowlist (`ready` only on `CLEAN`) was rejected: `UNSTABLE` (a`) —
so the absorption and the merge state describe one PR: check rows all green to
the watcher, commit status failing to GitHub. It holds for the life of the
head, on every poll of every watch. Derived from those two sites rather than
measured against a live advisory check; a PR carrying a `continue-on-error`
job that fails would confirm it in one `gh pr view`.

**The race, whose ordering this row had backwards.** The view read runs first
and the check buckets second
(`scripts/pr-sentinel-watch.sh:1306:IFS=$'\t' read -r STATE MERGE BASE HEAD_SHA PR_URL <<<"$gh_state"`
precedes `scripts/pr-sentinel-watch.sh:1366:checks=$(gh_pr_checks 2>/dev/null || true)`),
so a run registering *between* the two reads makes the buckets pending and
`green` 0 — the safe direction. The unsafe window is the opposite one: a run
registered before the view read with the checks endpoint still serving older
rows. That needs the checks endpoint to lag the view endpoint across
`PR_SENTINEL_GREEN_POLLS` consecutive polls, default 2, since any non-green
poll resets the streak
(`scripts/pr-sentinel-watch.sh:1491:(( green == 1 && GREEN_SEEN >= GREEN_POLLS )) && confirmed_green=1`).

## The decision

**Settles (answered):** derive the summary from the merge state, and add no
`UNSTABLE` hold — neither the unconditional form nor the transient
N-consecutive-polls form `BLOCKED` uses. Three things settle it from the repo.

*The unconditional hold is rejected on record.* `docs/DESIGN.md` turns down an
allowlist because `UNSTABLE` and `HAS_HOOKS` are legitimately mergeable and a
`docs/DESIGN.md:561:repo can sit in them indefinitely.` The durable route above
is that sentence's concrete instance, and the watcher ships the code producing
it.

*The transient hold buys latency and no new verdict.* `BLOCKED`'s hold works
because it releases into a distinct terminal event that refuses to call the PR
green (`docs/DESIGN.md:507:terminal **`blocked`** event that names both candidate causes and explicitly`).
An `UNSTABLE` hold has nowhere to release to — the PR is mergeable, so the
event after the wait is `ready` again. What it would add over
`PR_SENTINEL_GREEN_POLLS` is more of the same instrument, consecutive polls,
against a state the durable route holds forever: paid on every watch of every
PR with an advisory check, collected in none of them.

*Refusing to pick is this watcher's stance wherever it cannot separate two
causes.* `blocked_detail` says so
(`scripts/pr-sentinel-watch.sh:1103:# report deliberately does not guess which requirement it is — the watcher`)
and `unchecked_detail` repeats it
(`scripts/pr-sentinel-watch.sh:1145:# a reader take it for green. It names both causes and refuses to pick: the`).
When `gh pr checks` and `mergeStateStatus` disagree the watcher cannot tell
which is stale. A hold picks. Deriving the summary hands the disagreement to
the reader along with the command that settles it.

## What to build

The report changes; the guard's condition does not.

1. `emit_ready` and `notice_ready_watching` derive their summary from `$MERGE`.
   `CLEAN` and `HAS_HOOKS` keep today's wording. `UNSTABLE` says the check rows
   are all green **and** GitHub reports a non-passing commit status, names both
   causes — an advisory or non-required check failing, or a run that registered
   after these rows were read — and refuses to pick, in `unchecked_detail`'s
   shape.
2. On `UNSTABLE` the next action gains a confirmation step before the handback:
   `gh run list --commit <head>`, the separator `unchecked_detail` already
   prescribes. The handback stays — the PR may be perfectly mergeable.
3. `ready` stays terminal and stays in the Stop hook's concluded set. Nothing
   at `scripts/pr-sentinel-watch.sh:1529:&& [[ "$MERGE" != "BLOCKED" && "$MERGE" != "UNKNOWN" ]]; then`
   moves.
4. A watcher fixture with `mergeStateStatus: UNSTABLE` and all-green buckets,
   asserting the report carries no unqualified "all checks are green"; and its
   control, a `CLEAN` run that still does. `README.md`'s `ready` row gains the
   `UNSTABLE` wording, `docs/DESIGN.md` the reasoning above.

## How this composes with Q37

Both land on the same readiness guard and they do not fight, because this row
changes no condition there — only the two emit bodies. Q37 adds a branch inside
that guard selecting a different terminal event for a draft. One session
implementing both writes: the condition unchanged, one new draft branch within
it, and a `$MERGE`-derived summary in each emit body. Had this row taken the
transient hold they would have collided — a third counter beside `GREEN_SEEN`
and `BLOCKED_SEEN` in the same `if`, with an undecided ordering against the
draft test.
