# The Stop hook may count a reviewer as the owner of the PR it reviewed

During a parallel batch on 2026-11-10, the Stop backstop blocked an independent
reviewer session's turn over PR #188, which that session reviewed and did not
author. The reviewer opened no PR and pushed nothing, so by the rule in the
hook's own comment it should never have been blocked: a PR "merely referenced"
is in neither ownership set.

The hook's owned set is the PRs the session created plus every PR it launched
a watcher for (`scripts/pr_sentinel_stop_hook.py:893:owned = created | set(scan.pr_by_toolid.values())`).
The watcher half comes from a regex over the raw text of any backgrounded Bash
command (`scripts/pr_sentinel_watchers.py:217:for m in WATCH_ARG_RE.finditer(cmd):`),
with no tokenizing. So a backgrounded command that only *mentions*
`pr-sentinel-watch.sh 188` — in an `echo`, a quoted string, a heredoc, a
comment — would register the session as #188's babysitter.

That is a hypothesis. Nobody has read the reviewer's transcript to see which
backgrounded command, if any, matched. A reviewer that genuinely launched the
watcher would be owning the PR by design, and the block would then be correct.

**Measure:** read the reviewer session's transcript for every
`run_in_background` Bash call naming `pr-sentinel-watch.sh`, and say whether
the one that matched launched the watcher or only mentioned it. If it only
mentioned it, the fix is to read the command through the shared tokenizer the
guard and the PostToolUse hook already use, with a fixture for the mention
shape that fired. If it launched it, the question becomes whether launching a
watcher on someone else's PR should claim it, which is a design call for Karl.

## Why this ranks here

A wrong block costs a reviewer one turn and nothing worse, because the reviewer
can answer it and move on. It sits beside Q66, the other Stop-hook block that
buys nothing, and below the correctness rows.
