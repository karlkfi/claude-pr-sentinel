# A mutation sweep leaves a tree git reports as ordinary work

Inversion testing is how this repo establishes that a new test can fail: break
the product code, demand red, restore. Done in a loop it is a harness that
rewrites a tracked file in place, and between its backup and its restore the
working tree holds deliberately broken code.

Nothing marks that tree. `git status` says `M scripts/pr-sentinel-watch.sh`,
which is what it says about honest work in progress, and `git diff --stat`
counts lines — a mutation that swaps one string for an empty one, or a
condition for `false`, changes no line count at all. The only instrument that
separates the two is a byte comparison against a copy taken before the sweep
started.

## What was measured

2026-09-19, twice in one hour, on the branch adding Q44's base-comparison
report.

The first was a sweep killed by an overnight restart. The tree came back
carrying mutation 3 of 8 — one reason string blanked — and a `git diff --stat`
of `206 insertions, 3 deletions`, which is exactly the honest diffstat. An
instruction to commit the surviving work first would have committed it.

The second was a sweep stopped **deliberately**, four minutes in, to free the
machine. Same result: `base_comparison_note`'s two conditions replaced by
`false`, `git status` reporting a modified file and nothing else.

## What this changes

The rule that suggests itself — check the tree after a crash — is too narrow
and would have missed the second case. It is not a *killed* harness that leaves
this. It is any harness that mutates in place, and the window is every moment
between its backup and its restore, a deliberate stop included.

Two things follow, and the second is the one that generalises:

- **Verify by comparison, not by inspection.** `cmp` against the pre-sweep
  backup, or `git diff` of content where a commit already exists. `git status`,
  `git diff --stat`, and a glance at the file all report a mutant as ordinary.
- **A reader who has not seen the change cannot validate the tree either.**
  Shown `BASE_UNRESOLVED=""` with no knowledge of what that line should hold, a
  reviewer has no expectation to violate. Content-level review does not rescue
  this for anyone but the author, which makes it the author's check and nobody
  else's to delegate.

## Proposal

One candidate. A short section in `docs/development/testing.md` covering the
inversion loop: take the backup, restore from it, and verify by comparison
before any commit — with the two measurements above as the reason, since the
failure is invisible to every command a person would otherwise think to run.

Worth recording as a non-fix: having the harness write a sentinel file the
pre-commit hook refuses to commit alongside. It would work, and it is
machinery for a practice that currently has none — a paragraph that tells
someone what to check is the right rung first, and the gate is the answer if
the paragraph turns out not to hold.

The broader version of the second bullet is not repo-local: it is about an
orchestrating session giving a worker instructions about the worker's own
working state. That belongs in the dispatch contract rather than here, and this
row does not try to carry it.

## Why this ranks here

It has cost nothing yet — both instances were caught, one of them by a check
written in response to the other. What it costs when missed is a commit
carrying deliberately broken code with a green-looking diffstat, found later by
a test failure whose cause is nowhere near where it is reported.
