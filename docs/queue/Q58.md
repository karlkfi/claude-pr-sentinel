# Twenty-nine watcher tests race a three-second wall clock under load

`tests/test_watcher.py` runs the watcher as a real subprocess against a stub
`gh`, and twenty-nine cases bound it with a short real-time budget — twenty at
`PR_SENTINEL_TIMEOUT: "3"`, nine at `"4"`. Each asserts an event that takes
several polls to arrive. A poll is a subprocess call, so when the machine is
busy the polls stretch, the budget does not, and the watcher emits `timeout`
before the event the test is waiting for.

The harness owns half the fix. `run_watcher`'s `virtual_clock=True` stubs both
`sleep` and `date`, so the watch costs no *virtual* wall time and every sleep is
reported on stderr for `sleeps()` to read. Seven cases use it; the twenty-nine
do not. It is not the whole answer — see below, where a case that already uses
it failed anyway.

## What was measured

2026-09-18, on a machine also running a mutation sweep. `make check` failed two
cases that had passed on the same tree twenty-five minutes earlier:

```
FAIL: test_ready_watching_notice_reports_head_sha
  'PR-SENTINEL EVENT: ready_watching' not found in
  'PR-SENTINEL EVENT: timeout ... The watch budget (3s) elapsed'
FAIL: test_ready_withheld_on_unknown_merge_state
  "'ready' was withheld" not found in
  'PR-SENTINEL EVENT: timeout ... The watch budget (4s) elapsed'
Ran 586 tests in 355.058s
```

355s against 224s for the same suite on the same tree — 58% slower, and the two
failures are both budget-elapsed rather than a wrong verdict.

A second measurement the same day, from the session running the merged-set lint
on the same machine: its suite ran **2h33m against a normal four to six
minutes** at load average 12.58, and never finished. That is the stronger
exhibit — not two assertions flipping, but a whole suite failing to complete in
thirty times its normal wall time, on a machine doing nothing worse than running
two test sweeps at once. Re-run alone
straight afterwards, both passed, and one of them passed three times running.
The tree's only change in between was a comment in
`scripts/pr-sentinel-watch.sh` and two backlog files, so nothing in the diff
could reach either test.

## The virtual clock is necessary and not sufficient

Measured 2026-09-19, and it corrects the proposal above rather than supporting
it. `test_unchecked_waits_out_the_grace` **already uses `virtual_clock=True`**
and it still failed, on a different bound:

```
subprocess.TimeoutExpired: Command '['bash', '.../pr-sentinel-watch.sh', '123']'
  timed out after 20 seconds
Ran 596 tests in 384.808s   (load average 24.41)
```

That is `run_watcher`'s own `subprocess.run(..., timeout=20)`, not the watcher's
budget. The virtual clock stubs `sleep` and `date`, so it removes the race
between a poll streak and `PR_SENTINEL_TIMEOUT`. It does nothing about the real
CPU the polls consume, and the harness bounds that separately.

The mechanism is not the one that suggests itself. A long virtual budget does
**not** become a long real run: instrumented, that test's 600-second virtual
budget produced **20** real poll loops and 20 virtual seconds slept, because it
exits at the grace boundary. Twenty iterations that fork the stub cost 3.2
seconds idle and more than 20 under load. Nothing is looping away; a fixed
real-time bound simply fails once the machine is busy enough.

So moving a case to the virtual clock fixes the budget race and leaves it
exposed to `timeout=20`. Both bounds have to be dealt with, and the second one
is per-call in `run_watcher` rather than per-test.

## Not the whole twenty-nine

The population is the tests that set a short budget; the at-risk subset is the
ones asserting an event must arrive *before* it. A case that asserts `timeout`
itself fires is safe under load — a slow machine makes it more true, not less.
Separating the two is part of the work rather than a thing this row has done,
so treat twenty-nine as the population to walk, not the count to fix.

## Why it is worth doing rather than raising the budgets

Raising a budget trades a flake for a slower suite and buys no correctness; the
race is still there at a higher load. The virtual clock removes the dependency
instead, and it already exists, is already used, and already has the `sleeps()`
accessor that lets a test assert the pacing it actually cares about rather than
waiting for it.

One precedent in the tree: a Q43 case slept 1.5s against a one-second window and
went red on CI 3.10 and 3.11 while green locally. The repair was to construct
the aged state and state its age, not to sleep longer — the same move, applied
to one test.

## Why this ranks here

It costs a false red on a loaded machine, which is a gate that cries wolf: the
expensive failure is not the re-run but a session concluding its change broke
something it did not touch. Two cases did that today and cost one diagnosis
cycle. Nothing is wrong with the product and no user sees it, which is what
keeps it below the correctness items.
