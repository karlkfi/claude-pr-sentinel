# `ready` names no head SHA, so a stale watcher's report reads as current

`emit_ready` (`scripts/pr-sentinel-watch.sh:788:emit_ready() {`) prints the
event, the PR number, `State` and `mergeStateStatus`, and no commit. Two
watchers launched on the same PR at different heads therefore emit
byte-identical `ready` reports, so a session cannot tell one armed on the
current head from one armed on a head a push has already replaced.

Measured 2026-09-03 on pr-sentinel 0.9.0, watching `claude-spill-guard` PR 92:
one watcher launched at head `e53f99d`, a second after a push moved the head to
`3487a0f`, both exited `ready`, and the two outputs differ nowhere. It did not
bite — that session took its own `gh run list --commit <head>` and
`gh pr checks` readings against the current head and quoted that head in its
handback — but nothing in the report would have stopped it un-drafting on a
verdict taken against a commit no longer on the branch.

The asymmetry is one field. Six sites print `Head SHA` — `check_failure`
(`scripts/pr-sentinel-watch.sh:578:emit_check_failure() {`), the base-failure
notice, `conflict`, `behind`, `dequeued`, `blocked_detail` — and the three that
do not are the green-flavoured ones: `emit_ready`, `notice_ready_watching`
(`scripts/pr-sentinel-watch.sh:804:notice_ready_watching() {`), and the
`READY_REPORTED` branch of `emit_timeout`. The report a session acts on most
decisively carries the least provenance. `ready` does print `mergeStateStatus`,
so the SHA alone is missing.

The fix is one `echo` per site and no new GitHub read: `headRefOid` is already
in the watcher's query
(`scripts/pr-sentinel-watch.sh:223:--json state,mergeStateStatus,baseRefName,headRefOid,url`),
already parsed into `HEAD_SHA`, and in scope at both green emitters.

Distinct from #112, which asks whether checks ran at all rather than which
commit they ran on, and from #37, a race between one push and one watcher's
first poll that PR #39 closed by confirming green across two polls — two
*confirmed*-green watchers still report identically, so this survives that fix.
#37's plan rejected pinning the green *test* to `HEAD_SHA` because check rows
carry no SHA and it needs a second query shape
(`docs/plan/confirm-green.md`); printing a SHA the watcher already holds is a
different ask, and neither reason reaches it. [Q34](Q34.md) is the sibling —
the same missing-identifier class, one field over.
