# The suite's fixed subprocess timeouts flake under concurrent load

Two suites bound a subprocess with a hard wall-clock budget and treat expiry as
a result rather than as "could not measure":

| site | budget | symptom when it expires |
|---|---|---|
| `scripts/pr_sentinel_overlap.py:34` `PROBE_TIMEOUT = 5` | 5s per probe | the guard emits no deny, and the test's `json.loads('')` raises `JSONDecodeError: Expecting value: line 1 column 1 (char 0)` |
| `tests/test_watcher.py:160` `run_watcher(..., timeout=20)` | 20s per watcher run | `subprocess.TimeoutExpired: Command '[bash, pr-sentinel-watch.sh, 123]' timed out after 20 seconds` |

Measured 2026-08-19 on a workstation running eight concurrent worker sessions,
each shelling out through its own `make check`. Four runs of one unchanged
tree:

| run | result |
|---|---|
| `make check` | FAILED — 2 failures, 3 errors, all `test_overlap` |
| `tests.test_overlap` alone | 1 error — a *different* test |
| `tests.test_overlap` alone, again | 50 tests, OK |
| `make check` | FAILED — 1 error, `test_watcher.test_pending_polls_do_not_widen` |

A different test each time and never the same suite twice is the signature of a
wall-clock bound, not a logic bug; the same tree ran 393/393 green earlier the
same hour. Every failure traces to a timeout, none to an assertion about
behaviour.

Costs a wasted gate run per occurrence, and worse, invites a worker to "fix" a
test that was never broken. Cheapest shape: scale both budgets by an env knob
the harness can raise (`PR_SENTINEL_TEST_TIMEOUT_SCALE`), so a loaded box buys
time instead of failures. Raising them unconditionally is the wrong direction —
5s is a deliberate interactive budget, guarded by the comment on
`MAX_PR_DIFFS`: "this runs while someone waits".

The overlap half also has a code defect underneath it — see Q28, which is worth
fixing whether or not this row is.
