# Document the `pr-sentinel: ` opener every hook message carries

Every string this plugin hands back to a session — all three deny reasons, the
auto-allow reason, both PostToolUse nudges, the Stop block and its dampened
notice — opens with `pr-sentinel: `. Nothing user-facing says so. `README.md`,
`docs/DESIGN.md`, `PRIVACY.md` and `docs/development/` return nothing for that
string; the convention is recorded only in a code comment at
`scripts/friction-report.py:159-160` and in the test that pins it.

It is load-bearing rather than cosmetic. A deny leaves no record in the
decision stream — the guard's own comment at `scripts/friction-report.py:126-153`
works through why, and measures it: 893 transcripts, 52 denies recovered from
tool results, zero from the attachment stream. The error text handed back to the
agent is the only trace a deny leaves, so the opener is the key that recovers it.
`DENY_TEXT` at `scripts/friction-report.py:161` is built on exactly that, and
foreground-guard's own report parses the same opener across plugins.

So the convention has a reader outside this repo, which is what turns it from a
house habit into an interface. Someone adding a fifth decision branch here has no
document telling them the opener is required, and the code comment that says so
sits in the report rather than in the guard they are editing.

**Scope this to pr-sentinel.** State the plugin's own convention, and say that a
cross-plugin reader depends on it. Do not specify the cross-plugin contract
itself — foreground-guard owns the reader, so it owns that definition, and a
second normative statement of it here would be the thing that drifts. There is no
tracking link for that side yet; this row does not block on one, and whoever
picks this up should check whether one exists by then rather than treating its
absence as the current state.

Likely home is the **Activity report** section of `README.md`, next to the
follow-through and guard-decision bullets that already explain what the report
recovers and how. A sentence in `docs/DESIGN.md` on why a deny needs a
self-identifying opener at all would carry the reasoning; the README bullet only
needs the rule.

Two things worth checking rather than assuming when this is written:

- The opener is asserted for the guard's four reason builders. The nudges, the
  Stop block and `build_warning` conform today and are covered only indirectly,
  through the signature fixtures in `tests/test_friction_report.py`. If the doc
  states the rule for *every* message, widen the assertion to match it — a
  documented rule with a narrower test is the shape that goes stale quietly.
- This repo anchors its matcher with `\A`; foreground-guard uses `^`, which
  without `re.MULTILINE` holds only because no newline precedes the opener. Worth
  a note if the doc shows a matcher at all, so nobody copies the weaker anchor.

Filed from the Q5 batch, 2026-08-21, alongside the test that pins the guard's
four builders. A figure from that batch, measured by the orchestrating session
and not re-checked here: four of five sibling repos already conformed to the
opener, none of them documenting it anywhere.
