# The base-run reads take a fork PR's run as the base's

The watcher asks for "the base branch's runs" with
`actions/workflows/<wf>/runs?branch=<base>`. GitHub's `branch` filter matches a
run's `head_branch`, and a pull request opened from a fork's branch of the same
name has that `head_branch` too. So a fork contributor's PR from their own
`main` is, to this query, a run on `main`.

The site that costs a wake is `base_run_state`
(`scripts/pr-sentinel-watch.sh:589:		"${repo}/actions/workflows/${wf}/runs?branch=${BASE}&status=completed&per_page=1" \`),
the `per_page=1` read `base_failures_only` takes as the base's verdict. A
failed fork PR run that happens to be the latest completed one reads as "the
base is red", and the watcher then emits the non-terminal `base_failure` notice
instead of waking the session with `check_failure`. That suppresses a wake for
a failure that is the PR's own.

The same filter is in `base_run_duration`, which paces polls and costs only
timing, and in the fork-point reads the Q65 change added, where it costs walk
budget in the safe direction (the walk caps out and the report stays
`check_failure`).

## What was measured

2026-11-10, against the public `cli/cli`, whose base branch is `trunk`:

```
$ gh api "repos/cli/cli/actions/runs?event=pull_request&branch=trunk&per_page=20" \
    -q '"\(.total_count) total", (.workflow_runs[:5][] | "\(.event)\t\(.head_branch)\t\(.head_repository.full_name)\t\(.conclusion)\t\(.path)")'
40 total
pull_request	trunk	Momota-store/cli	failure	.github/workflows/go.yml
pull_request	trunk	Momota-store/cli	failure	.github/workflows/codeql.yml
pull_request	trunk	arletteramosg26-ux/cli	failure	.github/workflows/go.yml
pull_request	trunk	arletteramosg26-ux/cli	failure	.github/workflows/go.yml
pull_request	trunk	HIHACK1911/cli-go	failure	.github/workflows/go.yml
```

Every one of those is a fork's PR, and every one failed. Whether one was ever
the *latest* completed run of its workflow at the moment a watcher read it is
not measured. The same review measured it separately on `cli/cli` with
gh 2.103.3.

## Candidate fixes

- Add `event=push` to the query. That keeps only runs of commits that landed on
  the base. A repo whose base CI runs only on `merge_group` or `schedule` would
  then read no base run and fall through to `check_failure`, which is the safe
  direction but loses the comparison there.
- Or keep the query and drop runs whose `head_repository.full_name` is not the
  repo's own, in the `-q` projection. A full name is GitHub-controlled metadata,
  so this stays inside the watcher's field rules. A same-repo PR from a branch
  named like the base is still matched.

Whichever is taken goes in `PRIVACY.md`'s watcher section if it reads a new
field.

## Why this ranks here

A false "inherited" verdict hides a PR's own failure behind a notice that tells
the session to wait. That is the same direction of harm as Q65's misfire. It is
reachable on any repo that takes fork PRs, and on such repos fork PRs from a
same-named branch are routine.
