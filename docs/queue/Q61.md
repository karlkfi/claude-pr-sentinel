# No gate sees a new field in the watcher's `gh pr view --json` list

`CLAUDE.md` states the disclosure rule without qualification — a new GitHub
read "must be named in `PRIVACY.md`, in that component's own section — the
disclosure tests in `tests/test_watcher.py` fail the build otherwise". For a
field added to the watcher's one metadata query
(`scripts/pr-sentinel-watch.sh:288:--json state,mergeStateStatus,baseRefName,headRefOid,url \`)
no test fails, and none reports anything.

## Measured

2026-09-19 at `65a9700`. `isDraft` appended to that field list, `PRIVACY.md`
left untouched, then the whole suite:

    $ python3 -m unittest discover tests
    Ran 586 tests in 246.948s
    OK

The two tests that look like they cover it do not.

`test_every_graphql_read_is_named_in_privacy` reads GraphQL query blocks and
nothing else
(`tests/test_watcher.py:2310:for block in re.findall(r"-f query='(.*?)'", script, re.DOTALL):`),
so a `--json` list is never in its input. Its own docstring says as much and
gives the reason
(`tests/test_watcher.py:2307:is where the reads worth disclosing have actually appeared.`).
That was a fair reading of the history. The row proposing to fetch `isDraft` is
the case that ends it.

`test_never_queries_comments_or_body` is a denylist of five words
(`tests/test_watcher.py:2239:forbidden = ("body", "comments", "--comments", "reviews", "title")`),
so it is silent on any field nobody thought of. Its second assertion looks like
an allowlist and is a substring test
(`tests/test_watcher.py:2251:self.assertIn("state,mergeStateStatus,baseRefName,headRefOid,url",`)
under a comment reading "The one metadata query lists only the allowed,
GitHub-controlled fields" — which `assertIn` does not establish. Driven on
synthetic field lists the same day:

    state,…,url                 denylist fires: no    assertIn fires: no
    state,…,url,isDraft         denylist fires: no    assertIn fires: no
    state,…,url,title           denylist fires: YES   assertIn fires: no
    state,isDraft,…,url         denylist fires: no    assertIn fires: YES

Row three is the control: the denylist does fire, so the silence on `isDraft`
is coverage and not a broken harness. Row four is the trap — inserting a field
mid-list reddens on **position**, which reads to the author as the security
gate catching them when it is the substring moving.

## Distinct from its neighbours

Three rows already sit near this and none of their fixes closes it. The row on
gates that check a name appears rather than whether it describes the read is
about a weak assertion over an input the gate receives; this is about an input
no gate receives. The row on gates blind to writes is a different surface
again. The row on citation fragments is unrelated.

## What to build

Extend `undisclosed_reads`, or add a sibling, to parse the
`--json` field list and require each field to be named or described in
`PRIVACY.md`'s watcher section. `headRefOid` is the case that decides the
shape: `PRIVACY.md` describes it in prose as "head commit", not by field name,
so a bare name grep fails on the disclosure that is already correct. Either
accept a per-field alias table or check the field name and update `PRIVACY.md`
to carry it.

Ship it with both arms driven: a field added without disclosure must fail, and
the current tree must pass. Without the second the new gate could be one that
never goes green.

While the fix is out, `CLAUDE.md`'s sentence overstates what runs. Either
qualify it or land the gate that makes it true.
