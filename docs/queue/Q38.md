# A head predating the base's fix reads as this PR's own failure

`base_failures_only` (`scripts/pr-sentinel-watch.sh:486:base_failures_only() {`)
splits a failing check into two states. Red on the base too: inherited, so the
watcher emits the non-terminal `base_failure` notice and keeps polling. Green on
the base: this PR's own, so it wakes the session with `check_failure` and
`scripts/pr-sentinel-watch.sh:555:Next action: diagnose and fix the failing check(s) below in this local`.
The dispatch site has nothing in between
(`scripts/pr-sentinel-watch.sh:997:if (( BASE_CHECK == 1 )) && base_failures_only "$failed_links"; then`).

There is a third state it has no name for. A PR whose head predates the fixing
merge keeps failing on the inherited breakage after the base goes green, and
keeps failing until it is rebased. The test reads that as "green on the base,
still failing here" and hands the session a defect that is not its own.

1. Failing on the base and here. Inherited, wait. Handled today.
2. Green on the base, failing here, the head does NOT have the fix as an
   ancestor. Still inherited, and the correct instruction is "rebase". Missing.
3. Green on the base, failing here, the head DOES have the fix. This PR's own.
   Handled today.

`notice_base_failure` is right about the two states it names, and it is the
reason the failure below was handled correctly at all. Its closing paragraph
(`scripts/pr-sentinel-watch.sh:603:failure IS this PR's own and the next poll wakes this session with`)
promises exactly the transition the watcher then takes. The defect is a missing
third state, not a wrong rule.

## What was observed

One misfire, measured 2026-09-01 in `karlkfi/claude-skills` during a parallel
batch. Times are merge times read from `gh pr view`.

1. 04:59Z, #417 lands `brevity/SKILL.md` on `main` with frontmatter carrying an
   unquoted inline value with a colon in it.
2. 05:37Z, #409 lands a `validate-skills` check that rejects exactly that.
   `main` goes red on the merge result: `validate-skills: brevity/SKILL.md:
   "description:" is an unquoted inline value with a colon at offset 847`.
3. #410 was based on that red `main` and failed the identical job for the
   identical reason. Its watcher emitted `base_failure` and got it right,
   including what happens next.
4. 05:59Z, #420 fixes `brevity/SKILL.md`. `main` goes green.
5. The next poll took the branch that notice promised and woke the session with
   `check_failure`. But #410's head still predated #420, so it was still
   failing on the inherited breakage.

Followed literally, that instruction pushes a duplicate of #420 onto a branch
belonging to a different session, which is the same N-sessions-write-the-same-fix
cost issue #44 and PR #45 exist to prevent, arriving one state later. The
session did not follow it: it extracted `origin/main`, ran main's own
`validate-skills.py` over the tree, got `EXIT=0` with no `brevity` hit, and
concluded the failure was inherited. That is a session getting lucky, not a
guard working.

A second misfire was predicted during the same batch and did not occur. That
author's rebase completed before the watcher's next poll, so it only ever saw
the rebased head and reported green. One observed misfire, not two.

Nothing since the release has moved this. `base_failures_only`, its dispatch
block and `notice_base_failure` are byte-identical between the installed v0.9.0
and `main` at `3a16d5973662f1bca14e8eee6439b15ca9c46b88`. Line numbers above are
main's; they sit roughly 80 lines earlier in the v0.9.0 copy.

## Proposal

One candidate, not a prescription. Before attributing a failure to the PR,
check whether the head has the base's fix behind it.
`git merge-base --is-ancestor <base-tip> <head-sha>` is the direct form, "the
head predates the base branch's fixing merge" the cheaper approximation, and
the watcher already tracks both operands off one read
(`scripts/pr-sentinel-watch.sh:885:IFS=$'\t' read -r STATE MERGE BASE HEAD_SHA PR_URL <<<"$gh_state"`).
When the answer is no, the next action is "rebase onto ${BASE} and push", never
"diagnose and fix". The watcher also already knows the moment this becomes
decidable: it is the poll where the base flips green, which is the poll that
currently wakes the session.

One constraint on the mechanism rather than an objection to it. The watcher
shells out to `git` nowhere; every `git` string in it sits inside an
instruction echoed at the session. A local `git merge-base` is a new dependency
for it, where `gh api`'s compare endpoint stays inside the existing one.

Alternatives worth recording:

- Keep waking, and fix the next-action text only ("the base is green now; if
  your head predates the fix, rebase"). Cheapest change, but it leaves the
  model to make the same judgement call that went right here by luck.
- Do nothing, on the grounds that `mergeStateStatus` covers it. It does not. A
  PR failing on inherited breakage still reports MERGEABLE, which is what makes
  this route quiet.
- Have the watcher rebase for the session. Wrong for a watcher: the branch
  belongs to someone else's session and a rebase can conflict.

The pattern is not specific to pr-sentinel. In the same batch a base that had
moved produced four separate defects by four routes, each leaving a tree that
lints clean, gates green and reports MERGEABLE. This is the route with no
instrument on it at all.
