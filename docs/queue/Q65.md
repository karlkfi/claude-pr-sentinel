# `base_fixed` fires for any PR behind a green base, broken or not

`base_fixed` is meant for one state: the base was red, a fix landed, and this
head predates the fix. The watcher never checks the first half. It fires
whenever the base's latest completed run of the failing workflow is green and
the head lacks that run's commit, which is true of almost every failing PR on a
busy repo that is a commit or two behind. The failure is then routed away from
`check_failure`, so the session loses the CI log excerpt and is told "Do NOT
diagnose and fix it from here" about a defect that is its own.

The mechanism, on `main` at `9f74ac2`:

- `scripts/pr-sentinel-watch.sh:502:		"${repo}/actions/workflows/${wf}/runs?branch=${BASE}&status=completed&per_page=1" \`
  reads one run, the latest.
- `scripts/pr-sentinel-watch.sh:619:				BASE_GREEN_SHA="$sha"` records it when it is
  not red.
- `scripts/pr-sentinel-watch.sh:668:head_predates_base_green() {` asks only
  whether the head has that commit behind it.
- `scripts/pr-sentinel-watch.sh:1476:				elif head_predates_base_green; then`
  then emits `base_fixed`. Nothing on the path asks whether the base was ever
  red.

## What was measured

2026-10-04, `karlkfi/claude-bouncer` PR #205 at head `bbcf7cc`, pr-sentinel
0.12.0. The PR edited the exact source line its
`exit-status-guard-mutation-control` job asserts on, so it fails on any base.
The watcher reported, on two separate runs at that head:

```
PR-SENTINEL EVENT: base_fixed
Failed checks: exit-status-guard-mutation-control (fail)
Last main run: tests.yml (run 37267203531, 9f90e5c, success, 11m ago)
Base branch: main (this head does not have that run's commit behind it)
```

The base was green at the PR's own fork point too, read 2026-10-05:

```
$ gh api repos/karlkfi/claude-bouncer/compare/9f90e5c...bbcf7cc… -q '[.status, .merge_base_commit.sha[0:7], .behind_by]'
diverged  0f95e1f  2
$ gh api ".../actions/workflows/339873994/runs?head_sha=<0f95e1f full sha>"
37266874078  success  push
```

So the run that settles attribution — the base at the commit this head forked
from — exists and is green, and the PR owns the failure. The watcher never
looked at it.

## Proposal

One candidate. The `compare` call `head_contains` already makes returns
`merge_base_commit.sha` in the same response. Read the base's run of the same
workflow at that commit (`runs?head_sha=<merge base>`):

| Run at the fork point | Report |
|---|---|
| red | `base_fixed` — the head forked from a broken base that is now green |
| green | `check_failure` — the base worked where this branch started |
| none (path filter, never ran) | the open question below |

One extra `gh api` call, on the poll that already wakes the session, so once
per watch.

## Open questions for the implementer

- **No run at the fork point.** Path-filtered workflows skip most commits, so
  this case is common. Falling back to today's `base_fixed` keeps the bug for
  those workflows; falling back to `check_failure` re-opens Q38's case. Walking
  back to the nearest earlier base run the head contains is the honest answer
  and costs more calls.
- **`pull_request` runs test a merge ref.** A `pull_request`-triggered run
  checks out the head merged into the base as it stood when the run started,
  so it may already contain the green commit. If the failing run's event is
  `pull_request` and it started after the green run's commit landed, `base_fixed`
  is wrong by construction. The run's `event` and timestamps are
  GitHub-controlled metadata, so reading them stays inside the watcher's
  field rules.
- **A cheaper heuristic** — read `per_page=2` and require the run before the
  green one to be red — narrows the misfire but answers a different question
  (was the base recently broken) from the one that matters (was it broken where
  this head forked).

Any new read goes in `PRIVACY.md`'s watcher section; the disclosure tests fail
otherwise.

## Why this ranks here

A mis-attribution, and in the direction that costs most: it hides a PR's own
failure behind an instruction to rebase, strips the log excerpt, and on an
active repo it is the common case rather than the edge. Q66 is the Stop-hook
half of the same report.
