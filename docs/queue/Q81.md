# A stale, already-conflicting draft blocks an unrelated create

The overlap check denied a `gh pr create` over an open PR that was a six-week-old draft, already conflicting with `main`, and about something else entirely.
None of the exits the deny offers fit that case, so the create waited on Karl to approve a one-time override.
Q77 is the neighbouring row and does not cover this: its candidate escape has the create name the other PR as a known sibling, and #2084 was no more a sibling than it was superseded.

## What was measured

2026-11-28, in `actions-gateway/github-actions-gateway`, on installed pr-sentinel 0.13.0 (version read from `~/.claude/plugins/installed_plugins.json`).
The refused create was PR #2460's, for that repo's row Q1406, whose branch added a field to `ActionsGatewaySpec` in `api/v2/actionsgateway_types.go`.
The deny named #2084, a draft for an unrelated item (GKE Workload Identity to Artifact Registry).
Read at the refusal and again before the override, #2084 was `isDraft: true` and `mergeable: CONFLICTING` with `main`, last updated 2026-10-14, head `9046c0a0f`.
Its hunks in that file are `@@ -172,6 +172,24 @@` and `@@ -196,6 +214,46 @@`, and both PRs only add fields near each other.

The denial, verbatim but for two elisions:

> pr-sentinel: refusing `gh pr create` — this branch collides with an open PR: #2084 (api/v2/actionsgateway_types.go; a trial merge conflicts, or both make the same edit).
> A real collision is duplicated or mutually invalidating work, and review is an expensive place to find it.
> Read that diff first (`gh pr diff 2084`), then either fold this branch into that one or narrow it to what does not overlap.
> If this PR replaces that one, say so in the create's own --title or --body ("Supersedes #2084") and re-run; a PR named that way is not counted.
> A --body-file is not read.
> […]
> If the overlap is otherwise known and deliberate, re-run with an inline PR_SENTINEL_OVERRIDE=<reason> prefix […]
> Set PR_SENTINEL_OVERLAP_ENABLED=false to turn this check off, or name the paths every branch edits in PR_SENTINEL_OVERLAP_IGNORE.

Folding or narrowing was wrong, because the two items share nothing but a file.
"Supersedes #2084" would have been false, and the reviewer would have closed a live PR on it.
The override is forbidden to a worker session without a human's approval, so the worker asked Karl, who approved one inline `PR_SENTINEL_OVERRIDE` for that single create.

#2084 has been in this repo's denies before.
Q77's 2026-11-10 measurement, on 0.12.0, lists it among the path-only entries in the Q1322 workers' denies, which #179 has since stopped denying on.
So for as long as it stays open, #2084 is a standing hazard to any create whose branch edits lines near its hunks, and each hit costs one hand approval.

## What the check does today, read from the code

This part is a reading of `main` at `9a9d625` on 2026-11-28, not a measurement of the refused create.

- The open-PR query fetches no draft flag, age or mergeability, so a stale draft counts exactly like a fresh PR under review: `scripts/pr_sentinel_overlap.py:451:         '--json', 'number,headRefName,headRefOid,files') + repo_args(repo),`.
- The deny's basis text does not say which of its two causes fired, so whether this was a textual conflict or an identical edit is not recorded: `scripts/pr_sentinel_overlap.py:618:    MERGED: 'a trial merge conflicts, or both make the same edit',`.
  Two PRs adding different fields make an identical edit only by accident, so a textual conflict is the likely reading, and that is still an inference.
- The existing staleness discount is per path.
  A conflict the fork point shares with #2084 is subtracted, `scripts/pr_sentinel_overlap.py:410:        conflicts -= merge_conflicts(root, fork, head) or set()`, so being `CONFLICTING` with `main` discounts #2084 only on the paths where that conflict sits.
  Which paths those were for #2084 was not read.

## Two questions, unmeasured and undecided

Both are proposals.
Neither has been tried against this case or any other.

**Is a stale, already-conflicting draft in-flight work?** One shape counts a draft that is `CONFLICTING` with its base and has not been updated for some period as a report rather than a deny.
The period is unchosen, and so is whether all three conditions are needed or any one suffices.
`isDraft`, `mergeable` and `updatedAt` are GitHub-controlled metadata, so the `gh --json` field rule allows them, but each is a new GitHub read and needs its `PRIVACY.md` entry.
Against it: a draft can be parked work someone means to resume, and a branch that lands beside it leaves its author the rebase.
A report keeps that visible without stopping the create.

**Ask:** whether a stale draft may be reported rather than denied.
It turns on Karl because it loosens the deny's default, which `CLAUDE.md` puts behind his sign-off.

**Is a conflict from adjacent additions a collision?** The deny defines a collision as "duplicated or mutually invalidating work".
Two PRs that each insert lines at neighbouring spots conflict in git, and the second to merge has a trivial resolution, but neither duplicates nor invalidates the other.
One shape reports instead of denying where every conflicting hunk on both sides removes no lines.
Against it: two PRs adding the same field in different words are also pure additions, which is the duplicate the check exists to catch, and `same_edits` only catches the identical case.

**Measure:** replay `git merge-tree --write-tree` of #2460's branch against #2084's head `9046c0a0f` in a checkout of that repo, to settle whether the file conflicted or the identical-edit rule fired, and whether every conflicting hunk was additions only.
That decides whether this question applied to the measured case at all.

Done is a decision on each question, a test in `tests/test_overlap.py` that replays this case with whatever was chosen (a stale conflicting draft, or an additions-only conflict, reported instead of denied, and a fresh PR with the same diff still denied), and updated README PreToolUse rows and deny text.
