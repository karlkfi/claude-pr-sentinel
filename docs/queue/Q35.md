# PR_SENTINEL_WATCH_UNTIL has no per-launch route past the auto-allow

`PR_SENTINEL_WATCH_UNTIL` can only be set through the environment, so one
machine cannot hold two values for it at once. The dispatch design needs
exactly that. A worker session is deliberately left at the default `ready` so
its watcher exits and the session stops reading as busy — a live background
task hides the PR status icon a maintainer scans the session list for. The
orchestrator wants `closed`, so it keeps watching through review and wakes the
worker when the PR merges. Neither settings file reaches that: `settings.json`
is per-machine and a project `.claude/settings.json` is per-repo, and
orchestrator and workers share both.

The watcher reads the flag from the environment and nowhere else, at
`scripts/pr-sentinel-watch.sh:118:WATCH_UNTIL=$(printf '%s' "${PR_SENTINEL_WATCH_UNTIL:-ready}"`,
clamping anything that is not `closed` back to `ready` on the next line. Its
usage line takes one argument and no flags:
`scripts/pr-sentinel-watch.sh:50:# Usage: pr-sentinel-watch.sh <pr-number-or-url>`.

## The inline route defeats the guard's own auto-allow

That leaves the inline prefix as the only per-launch route, and the guard does
not recognise one. `watcher_launch_pr` requires exactly three tokens —
`scripts/pr_sentinel_guard.py:157:if len(argv) != 3:` — with `argv[0]` basename
`bash`, `argv[1]` realpath-equal to this plugin's watcher, and `argv[2]` a bare
positive integer or a github.com PR URL. Measured 2026-08-23 against current
`main`:

| command | tokens | `watcher_launch_pr` |
|---|---|---|
| `bash <watcher> 20` | 3 | `'20'` |
| `PR_SENTINEL_WATCH_UNTIL=closed bash <watcher> 20` | 4 | `None` |
| `PR_SENTINEL_WATCH_UNTIL=closed bash <watcher> <PR URL>` | 4 | `None` |

`=` is not in `_AUTOALLOW_FORBIDDEN`, so the prefix is not rejected as a
forbidden character. It fails on the count alone.

Two things follow from that `None`, and only the first is obvious. The
auto-allow at
`scripts/pr_sentinel_guard.py:424:if _autoallow_enabled() and is_watcher_launch(command):`
does not fire, so the launch falls through to the base Bash permission and an
unattended session stalls on a prompt. The duplicate-watcher deny at
`scripts/pr_sentinel_guard.py:408:launch_pr = watcher_launch_pr(command)` reads
the same function, so an env-prefixed relaunch also skips the "already watching
this PR" check and can start a second watcher for a PR that already has one.

## The asymmetry is the finding

`_strip_env_prefix` is in that same file, documented at
`scripts/pr_sentinel_guard.py:196:Drop leading NAME=VALUE assignments so`, and
five call sites on the deny-classification path use it. The auto-allow path
does not. The file already knows how to see past an env prefix; one of its two
consumers never learned.

There is precedent, and it is the same shape. Issue #27, "PR_SENTINEL_OVERRIDE
inline prefix is honoured inconsistently", was fixed by PR #28,
"fix(guard): honour an inline PR_SENTINEL_OVERRIDE prefix", on 2026-08-02. An
inline prefix the guard failed to see was accepted as a bug then; the
auto-allow path never got the same treatment. The flag itself came from issue
#23, closed 2026-07-27.

## Three candidates, and this row is not choosing

Every one of them widens a boundary or grows surface, which makes the pick a
maintainer's call rather than a filing session's:

1. **Call `_strip_env_prefix` in `watcher_launch_pr`.** Smallest diff, reuses
   code already in the file, and fixes the duplicate check in the same move.
   It also auto-allows the watcher launch under *any* env prefix, which is a
   real widening of what runs without a prompt.
2. **Give the watcher a `--until closed` flag.** This does *not* leave the
   guard alone: `bash <watcher> --until closed 20` is five tokens, so
   `watcher_launch_pr` has to learn the shape either way. What it buys is the
   narrowness of what it learns — one known flag over a two-value allowlist,
   rather than an arbitrary leading assignment. The cost is new CLI surface
   and a second way to express one setting.
3. **Strip only an allowlist of `PR_SENTINEL_*` assignments.** Narrowest
   widening of the three and the most code, with a list that goes stale as
   variables are added.

Whichever wins, `tests/test_guard.py` needs the prefixed launch as a case in
both directions — allowed with the prefix, still refused with a foreign one.
