# `ready` fires on a draft pull request

A draft PR whose checks go green gets the terminal `ready` report
(`scripts/pr-sentinel-watch.sh:1075:echo "All checks are green and the PR has no merge conflict. Nothing left to"`),
whose next action is "hand back to a human for merge review". A draft is not
available for merge review, and the readiness guard cannot see that it is one:
it tests the merge state alone
(`scripts/pr-sentinel-watch.sh:1529:&& [[ "$MERGE" != "BLOCKED" && "$MERGE" != "UNKNOWN" ]]; then`),
and `mergeStateStatus` does not observe draft status.

Measured on this repo's own PR #111, holding every other input constant. Same
PR, same head SHA, base `main`, checks green, minutes apart, flipping only the
draft bit:

| `isDraft` | `mergeStateStatus` |
|---|---|
| false | `CLEAN` |
| true | `CLEAN` |

Then a watcher launched cold against that PR, `isDraft: true` throughout the
run, exited `PR-SENTINEL EVENT: ready`.

The field is blind rather than merely unread. `MergeStateStatus` has no `DRAFT`
value at all — re-derived 2026-09-19, unchanged:

```
$ gh api graphql -f query='{ __type(name: "MergeStateStatus") { enumValues { name } } }'
DIRTY UNKNOWN BLOCKED BEHIND UNSTABLE HAS_HOOKS CLEAN
```

So no widening of the guard's denylist can reach this. That is the difference
from Q36, the same symptom from the opposite cause: `UNSTABLE` is a value the
denylist could name and does not, whereas draft is not a value at all. The
watcher would have to fetch `isDraft`, which
`scripts/pr-sentinel-watch.sh:288:--json state,mergeStateStatus,baseRefName,headRefOid,url` does not.

The wrong sentence is the smaller half. `ready` is terminal and joins the Stop
backstop's concluded set
(`scripts/pr_sentinel_stop_hook.py:142:r'PR-SENTINEL EVENT:\s*(?:ready|closed|blocked|unchecked)`,
consumed at `scripts/pr_sentinel_stop_hook.py:811:if CONCLUDED_EVENT_RE.search(_report_header_region(text)):`),
so the PR reads as handed off and the backstop stops blocking on it
(`README.md:196:opened a PR this session (or watched one), **no** live watcher, PR not handed off`).
A draft is the one shape where more pushes are expected by definition — parking
work-in-progress is what drafting is for — so the watch ends exactly where
babysitting still had a job.

## The decision

**Settles (answered):** fetch `isDraft` and give a green draft its own terminal
event. No hold — and not the `notice_ready_watching` shape this row proposed,
which is the trap rather than the escape from it.

*The `BLOCKED` trap does not transfer, because the party who clears a draft is
the session being watched.* `docs/DESIGN.md` rejects refusing `ready` on
`BLOCKED` and saying nothing more, because
`docs/DESIGN.md:495:a fully green PR would then never fire` at all and the
watcher burns its whole budget. That holds for `BLOCKED` because a third party
clears it — a reviewer approving, a workflow registering — so the watcher has
something to wait for. A draft clears when the author runs `gh pr ready`, and
the author is the session the watcher is about to put back to sleep. There is
nothing to wait for, so a terminal report is not a compromise here: it is the
complete answer, and the session can act on it the moment it wakes.

*Which is why this row's own preferred answer walks into that trap.*
`notice_ready_watching` is non-terminal, so the session does not wake, and it
is reached only under `PR_SENTINEL_WATCH_UNTIL=closed`
(`scripts/pr-sentinel-watch.sh:1530:if [[ "$WATCH_UNTIL" == "closed" ]]; then`).
Extending it to default mode leaves a green draft polling quietly until the
author — asleep, because nothing woke them — undrafts it, or the budget
elapses and the watch ends in `timeout`. That is the regression
`docs/DESIGN.md:497:repos that also have path-gated required checks.` records
for `BLOCKED`, reached by the route this row proposed to avoid it.

*Terminal means joining the concluded set, on the record already made for
`blocked` and `unchecked`*
(`docs/DESIGN.md:567:Leaving it out would have the hook re-block every stop and`
the session relaunch a watcher that reports the same thing). A `ready_draft`
the backstop does not recognise livelocks the same way: the watcher re-fires it
after `PR_SENTINEL_GREEN_POLLS` polls, indefinitely.

## The security question, and what does not enforce it

This row's argument — `isDraft` is a GitHub-controlled boolean, so it does not
cross the line `CLAUDE.md` draws at `body`/`comments`/`reviews`/`title` — holds.
Checked 2026-09-19 against the test that enforces it: the forbidden list is
exactly those five words
(`tests/test_watcher.py:2239:forbidden = ("body", "comments", "--comments", "reviews", "title")`),
and a boolean carries no attacker-writable text.

What the row did not say is that nothing enforces the other side either:
`isDraft` appended with `PRIVACY.md` untouched passes all 586 tests, measured
the same day. Two consequences land on whoever implements this, so they are in
the build steps below rather than here — the disclosure is hand-carried, and
the one way to make CI red is to insert the field mid-list, which is not the
security gate firing. Filed separately as Q61.

## What to build

1. Append `isDraft` to the field list at
   `scripts/pr-sentinel-watch.sh:288:--json state,mergeStateStatus,baseRefName,headRefOid,url`,
   to the `-q` projection beside it, and to the `IFS=$'\t' read` that unpacks
   it. **Append, never insert** — and not for a security reason.
   `test_never_queries_comments_or_body`'s second assertion is a substring
   check against the current list
   (`tests/test_watcher.py:2251:self.assertIn("state,mergeStateStatus,baseRefName,headRefOid,url",`),
   so a field inserted mid-list reddens on **position**. That red is the
   substring moving, not the security gate catching you — the gate is the
   five-word forbidden list, and `isDraft` is not on it either way.
2. Inside the readiness guard, ahead of the `WATCH_UNTIL` test, branch on the
   draft flag to a new terminal `ready_draft`. The guard's own condition does
   not move — which is what keeps this compatible with Q36.
3. `ready_draft`'s report says the checks are green, says the PR is a draft,
   and gives the next action as reviewing it and running `gh pr ready` when the
   session means to hand it back — never "hand back for merge review". Its
   `closed`-mode counterpart is `ready_draft_watching`, matching every other
   event's pairing.
4. Add `ready_draft` to `CONCLUDED_EVENT_RE`. Verified 2026-09-19 that the
   `(?![\w-])` lookahead behaves on both halves: with `ready_draft` in the
   alternation, `ready_draft` matches and `ready_draft_watching` still does
   not, in either alternation order.
5. **Hand-carry the disclosure — no test will make you.** `PRIVACY.md`'s
   watcher section
   (`PRIVACY.md:94:purpose. It issues read-only queries for:`) gains `isDraft`
   in the `gh pr view` bullet. Measured at `65a9700`: `isDraft` appended with
   `PRIVACY.md` untouched passes all 586 tests.
   `test_every_graphql_read_is_named_in_privacy` reads `-f query=` blocks and
   never sees a `--json` list; `test_never_queries_comments_or_body` is the
   five-word denylist above. Green CI here does not mean disclosed. Q61
   carries the gate gap.
6. `README.md`'s decision table gains `ready_draft` and `ready_draft_watching`;
   `docs/DESIGN.md` gains the asymmetry above. Fixtures: a green draft exits
   `ready_draft` and not `ready`, with a non-draft control on the same fixture
   exiting `ready` — without the control the new fixture cannot show it is the
   draft bit doing the work.

## How this composes with Q36

Both land on the same readiness guard and they do not fight. Q36 decided
against any `UNSTABLE` hold, so it changes no condition in the guard — only the
bodies of `emit_ready` and `notice_ready_watching`. This row adds one branch
inside the guard. A session implementing both writes the condition unchanged,
one draft branch within it, and a `$MERGE`-derived summary in each emit body —
including `ready_draft`'s, which needs the same treatment for the same reason,
since a draft can be `UNSTABLE` too.
