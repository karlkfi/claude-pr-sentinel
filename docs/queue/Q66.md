# One terminal report at the current head still draws a Stop block

The Stop backstop dampens a terminal event only once two separate watcher runs
have reported it at the same head
(`scripts/pr_sentinel_stop_hook.py:857:                         if len(runs) >= 2), None)`).
After the first report it blocks again with "no pr-sentinel watcher is tracking
it", and the relaunch it asks for exits within seconds with the identical
report. The second block buys nothing: the watcher already said what is wrong
at this head, and only a push can change that.

## What was measured

2026-10-04/05, `karlkfi/claude-bouncer` PR #205 at head `bbcf7cc`, pr-sentinel
0.12.0, from the session's own transcript. The session had a fix committed
locally and was running a six-minute repo gate before pushing.

```
05:29:33Z  Stop block: no watcher tracking #205      (no watcher since the push — fair)
05:29:58Z  relaunch -> PR-SENTINEL EVENT: base_fixed
05:30:04Z  Stop block: no watcher tracking #205      (one report: not dampened)
05:30:36Z  relaunch -> PR-SENTINEL EVENT: base_fixed (second report: dampened from here)
```

So the loop is bounded, as designed: two blocks, then quiet. The reporter read
it as unbounded because both blocks arrived while the gate ran. The cost is one
wasted relaunch per terminal event, on every dampenable event, not only
`base_fixed`.

## Proposal and the question it raises

The reporter's proposal: treat one terminal report at the PR's current head as
coverage until the head moves. That drops `>= 2` to `>= 1` for the dampenable
events.

What needs deciding before that lands is why the threshold was two. The
module docstring frames dampening as "two separate watcher runs ... same head
SHA ... the session has pushed nothing", which treats the second report as the
proof that the session saw the first and chose not to push. With one report,
the hook cannot tell a session that read the report from one that never looked
at the output file. Whether that distinction is worth a relaunch is the
judgement call; the original reasoning sits with issue #9 and #50.

**Ask:** whether one report at an unmoved head is enough proof that the session
has seen it. Read #9 and #50 first; if either names a case where the second
report carried information the first did not, that settles it as no.

Related but separate: Q57 makes the *watcher* record the heal events and quiet
a repeat. That changes what the second relaunch prints, not whether the second
block fires.
