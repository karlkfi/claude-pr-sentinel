Wake your session on CI failures and merge conflicts — no foreground polling, no comment-channel injection.

> [!NOTE]
> **A repeated `conflict`, `behind`, or `dequeued` now dampens the Stop hook, the way a repeated `check_failure` already did.** Until this release only `check_failure` dampened, so a watcher re-reporting the same conflict at an unmoved head blocked the end of every turn — and it bit hardest in the state where the session had *already* healed the branch and was waiting on its own local gate, with nothing to push. Patch release: no new events, no new configuration, nothing removed.

## Highlights

**[Dampening now covers every terminal event that asks you to push](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.8.1/README.md#what-it-does).** The rule is unchanged in shape. Two watcher reports of the identical event at the same head commit means the session pushed nothing in between, so the hook allows the stop with a non-blocking warning instead of re-blocking forever. What changed is the set it applies to: `conflict`, `behind`, and `dequeued` join `check_failure`. The non-terminal notices (`base_failure`, `ready_watching`, `blocked_watching`) are deliberately excluded, because the watcher keeps polling past them and they are never the report a stop is blocked over.

**A repeated heal event usually means the opposite of a repeated failure, and the warning now says which one it is.** A repeated `check_failure` is a check this session *cannot* fix: inherited from the base, out-of-scope, external, or misconfigured. A repeated `conflict` or `behind` is normally the reverse. The rebase is done and committed locally, the project's gate is still running, the remote is still `DIRTY`, and a relaunch has no move available at all. Reported from a live session on a six-minute gate, that gap cost three watcher launches and two blocked turns doing nothing (#50).

**`conflict`, `behind`, and `dequeued` reports now carry a `Head SHA:` line.** `check_failure` already had one; the heal events did not, which is why they could not dampen. It earns its place twice — without it, two conflict reports are byte-identical whether the base branch just moved or the session is mid-gate on a heal it already committed, so neither the hook nor a human reading the transcript afterwards can tell them apart.

## Upgrading

**No action required.** Nothing is removed, no configuration is renamed or added, and the hook's `additionalContext` shape is unchanged.

**One additive change to the report format.** The `conflict`, `behind`, and `dequeued` reports gained a `Head SHA:` line between `mergeStateStatus:` and `Base branch:`. Anything that greps a watcher report by `PR-SENTINEL EVENT:` or by field name is unaffected; anything matching those three headers by exact line count is not.

**One behaviour change to be aware of.** A PR whose watcher reports the same `conflict`, `behind`, or `dequeued` twice at one head commit will now let a turn end, with a warning naming the event, rather than blocking. As before, the hook never *silently* walks away from an open PR.

## Trust boundary

**No new reads, no new writable channel, no new network calls.** The watcher's `gh --json` field list is untouched — still GitHub-controlled metadata only, still no PR body, comments, reviews, or title. The Stop hook remains purely local: it reads the session transcript and each watcher's own output file, nothing else.

The one security-relevant detail in the change is that the widened signature keeps the same guard the narrow one had. The event marker, `Head SHA:`, and `Failed checks:` are matched **only in the header region above the `BEGIN CI LOG EXCERPT` banner**, so a forged copy of a report inside a semi-untrusted CI log cannot drive dampening. Where a file carries a notice before its terminal event, the signature reads from the **last** marker forward, so an earlier `base_failure` cannot donate its fields to the event being dampened. No security advisory accompanies this release.
