Wake your session on CI failures and merge conflicts — no foreground polling, no comment-channel injection.

> [!WARNING]
> **On 0.10.0 the duplicate-watcher guard could refuse a session's *first* watcher launch, leaving the pull request with no watcher at all.** The deny reads "the running watcher will wake you", so the session believes it and never retries — and the same poisoned entry disarmed the Stop hook backstop meant to catch exactly that. It is a race, so it does not fire every time. Everyone on 0.10.0 should take this release (#126).

> [!IMPORTANT]
> **`ready` no longer fires on a head that no check has reported on.** An empty check set used to read as green, because zero failures and zero pending look identical whether CI is slow to register or the repository runs none. If your repository runs no CI on pull requests, you will now get the new terminal **`unchecked`** event after `PR_SENTINEL_UNCHECKED_GRACE` seconds (default 600) where you used to get `ready` (#129).

## Highlights

**[A session's own in-flight launch is no longer read as a live watcher](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.11.0/README.md#what-it-does).** Claude Code writes the in-flight Bash `tool_use` entry to the transcript *before* it runs the PreToolUse hook, and the duplicate-watcher scan had no self-exclusion — so the launch being judged could count as the watcher already running. A refused call never starts a task, so no completion notification is ever written and the entry stays live for the rest of the session. The scan now excludes the call it is deciding on. Over the 400 most recently modified transcripts, 1 session had its first launch refused and 268 did not; do not read that as a bound on how often it bites, since the session that wrote the fix hit it on its own first launch (#126).

**[An empty check set is never green, and a head that stays empty gets its own event](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.11.0/README.md#a-head-no-check-reported-on).** `ready` now requires at least one check row that reported, whatever `mergeStateStatus` says — that alone ends the false handoff. A head still carrying no row after `PR_SENTINEL_UNCHECKED_GRACE` seconds gets the new terminal **`unchecked`** report, which names both causes and refuses to pick between them: the repository runs no workflow on this pull request, or GitHub never started the run. The grace paces the report, never the verdict — firing early states something true, where an early `ready` states something false. Ten minutes is roughly eight times the slowest healthy registration measured across a one-workflow repo and a thirty-nine-workflow one, and well inside the incident band that produced the four false handoffs this came from (#129, from #112).

**[The Stop hook follows a watcher's redirect path when it was built from a shell variable](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.11.0/README.md#what-it-does).** A watcher launched as `> "$S/sentinel.log"` wrote its terminal report to a file the hook declined to resolve, so a **merged** pull request kept blocking the turn as open — and the escape the block offers is written for the open-and-green case, not for a PR that is finished outright. A `$VAR` in a redirect target now expands against a `NAME=<literal>` assignment earlier in the **same command string**, which is the same model-authored source the path itself comes from, never the hook's own environment. Every decline that made the old rule safe survives: a value carrying `$` or a backtick is not a literal, a single-quoted `'$S/w.log'` is a filename, an assignment after the redirect does not count, and any `$` surviving expansion still declines rather than guess (#127).

**[A push to a filesystem remote no longer earns a nudge](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.11.0/README.md#what-it-does).** Pushing to a bare repo in a session's own scratchpad got the PR-babysitting nudge, which asks for a watcher against a pull request number the session would have to invent. The push target is now resolved against the local repo — `git remote get-url --push` for a named remote, git's own `pushRemote` / `pushDefault` / `remote` / `origin` order for a refspec-less push — and the nudge stays silent when it names a filesystem path or `file://`. Anything reachable over a network still nudges, whatever the hostname, because `gh` serves GitHub Enterprise under its own and an allowlist would silence real work (#128, closes #106).

## Upgrading

**Nothing to do.** No removals, no renames, no configuration change required. A plugin install carries everything.

**One new knob.** `PR_SENTINEL_UNCHECKED_GRACE` (default `600`) sets how long a head may carry no check row before the watcher reports `unchecked`. It paces that report only — an empty check set is never `ready` whatever this is set to. Raise it in a repository whose runs routinely take longer than ten minutes to register; `0` reports on the first empty poll.

**Two new event names, none removed or renamed.** The set goes from twelve to fourteen: the terminal `unchecked`, and the `unchecked_watching` notice its `PR_SENTINEL_WATCH_UNTIL=closed` counterpart emits. A session matching on `PR-SENTINEL EVENT:` headers or field names gains two values it did not have and loses none. `unchecked` is terminal and counts as a handoff to the Stop hook, for the same reason `blocked` does — telling its two causes apart means looking at the repository's workflows, which no amount of further polling answers. `gh run list --commit <head>` is the one command that separates them.

**If you run no CI on pull requests, this changes what you see.** Those repositories used to reach `ready` on the merge state alone and will now reach `unchecked` after the grace. That is the intended reading: nothing tested the code, and the report says so instead of handing off as green.

## Deprecations

**Nothing is deprecated, and nothing user-facing was removed.** No configuration key, event name, report field, or script path went away this window.

The other two are long-standing: the empty check set has read as green since v0.1.0, and the push nudge has never read the remote.

**Fixes (4)**

- Watcher: never report `ready` on a head no check has reported on, and report the new terminal `unchecked` event when one stays empty past `PR_SENTINEL_UNCHECKED_GRACE` (#129)
- Stop hook: resolve a watcher's redirect path when it was written through a shell variable the same command assigned, instead of declining the route and blocking on a merged pull request (#127)
- PostToolUse hook: don't nudge on a `git push` whose target is a filesystem path or `file://`, since nothing there can hold a pull request (#128)

## Trust boundary

**No new GitHub read, and the `gh --json` field list is untouched.** It still cannot reach `body`, `comments`, `reviews`, or `title`, and `tests/test_watcher.py` still fails the build if it does. The overlap check remains the only part of the hooks that talks to GitHub.

**Two new local git reads, both disclosed.** `git config --get` and `git remote get-url` in your working directory, used only to classify a push target as a forge or a filesystem path. A remote's URL is read to make that decision and is never emitted. `PRIVACY.md` names both in the PostToolUse hook's own section, which the disclosure tests enforce.

**The new redirect-path expansion reads no environment.** A `$VAR` in a watcher's redirect target resolves only against a literal assignment earlier in the same command string — the model wrote both halves — and never against the hook's own environment. Anything it cannot resolve to a literal declines the route, as before.

**No security advisory accompanies this release**, and no dependency bumps: the plugin is stdlib Python and POSIX-ish bash, and depends on nothing but `gh`.
