> [!IMPORTANT]
> **Through 0.11.0 the overlap check denied a `gh pr create` from a branch stacked on another open pull request — every time.** A stacked branch carries its parent's hunks by construction, and the check numbered it from the default branch, so the parent's lines were charged to the child and reported as an overlap on lines the child never touched. The `--base` on your create now settles it: declare the parent's branch and this branch is numbered from there, with the parent skipped as inherited work (#131).

## Highlights

**[A stacked branch is numbered from the base its create declares](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.11.1/README.md#overlapping-pull-requests).** The overlap check had no per-branch notion of a base — `PR_SENTINEL_BASE_REF`, else `origin/HEAD`, else `origin/main`, all of which name one ref for every branch in the repo — so a child stacked on an open pull request was always compared against the default branch and always collided with its own parent. Worse, once that parent rebased, the two sides were numbered in different pre-images: a 10-line shift on the base produced a false negative and a 28-line shift a false positive, so the verdict was arbitrary rather than merely wrong. The `--base` on the `gh pr create` is the only place a stack is written down — the repo's refs cannot tell one from an ordinary branch — so the guard now passes it through, and the check resolves it against the remote first, since a local branch of that name is routinely stale. A parent rebased out from under this branch leaves nothing comparable, so the check declines outright rather than guess. Declaring no base is unchanged and stays correct: such a create targets the default branch, so the pull request really would carry the parent's commits (#131, closes Q26).

## Upgrading

**Nothing to do.** No removals, no renames, no new configuration. A plugin install carries everything.

**To get the fix, declare `--base` on a stacked create.** `gh pr create --base <parent's branch>` is what tells the check this branch is stacked; without it the behaviour is what it always was, and correctly so. `PR_SENTINEL_BASE_REF` still works and is still one value for every branch in the repo, so a declared `--base` now wins over it.

**One behaviour to expect on a stale stack.** If the parent has been rebased and you have not restacked onto it, the check declines and stays silent instead of reporting. That is deliberate — the two branches are numbered in different pre-images, so any comparison between them is meaningless — and it means a genuine duplicate can go unreported until you restack. Fail-open, as every probe in this check is.

## Trust boundary

**No new GitHub read, and the `gh --json` field list is untouched.** It still cannot reach `body`, `comments`, `reviews`, or `title`, and `tests/test_watcher.py` still fails the build if it does. The overlap check remains the only part of the hooks that talks to GitHub, and it still issues the same two queries: `gh pr list --json number,headRefName,files`, and `gh pr diff` for at most three pull requests already sharing a path.

**One new local git read, disclosed.** `git rev-parse --verify` in your working directory, to decide whether a declared base resolves against the remote, alongside the `git merge-base --is-ancestor` that asks whether this branch is built on top of it. `PRIVACY.md` names both in the overlap check's own section, which the disclosure tests enforce.

**The declared base is a branch name off the command line, never PR text.** It comes from the `gh pr create` the session itself wrote, read out of the same simple command that matched the create so a `--base` belonging to another command in the chain is not borrowed. Nothing about the parent pull request beyond its head branch name and changed paths is read.

**No security advisory accompanies this release**, and no dependency bumps: the plugin is stdlib Python and POSIX-ish bash, and depends on nothing but `gh`.

That pass caught a hole the first round missed: with the parent-skip in place, `base_ref` itself was untested, because skipping the parent by name still leaves the branch compared against every *other* open pull request using a range set that contains the parent's lines. `test_the_parents_lines_are_not_charged_to_this_branch` covers that case.

Unchanged from v0.11.0: no test asserts a real `gh pr create` against a live GitHub repository. Every `gh` response is fixture-pinned through the stub.
