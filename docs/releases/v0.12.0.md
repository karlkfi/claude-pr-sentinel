Wake your session on CI failures and merge conflicts — no foreground polling, no comment-channel injection.

> [!IMPORTANT]
> **A relaunched watcher no longer wakes you for a failure it already reported.** If an earlier run reported the same `check_failure` on the same head commit with the same failed checks within the last hour, the watcher now emits a `repeat_failure` notice and keeps polling instead of exiting. The first report of a failure always wakes, and a push or a check flipping either way ends the dampening. `PR_SENTINEL_DAMPEN=0` restores the old behaviour (#136).

> [!WARNING]
> **Through 0.11.1, a push written as `git -C <path> push …` was never watched.** Git's own options before the subcommand shifted every word one place, so the hook never saw `push`, and it sent no nudge for the life of the branch. `-c`, `--git-dir`, `--work-tree` and `--namespace` did the same. The pushes were not refused and nothing in the session suggested they were missed (#156).

## Highlights

**[A relaunch over a failure you already declined notices instead of waking](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.12.0/README.md#a-relaunch-over-a-failure-you-already-declined).** A watcher keeps nothing between runs. So when a session had seen a failure, judged it not its own and left it alone, every relaunch found the same red and exited within seconds to report it again. The only way to end the turn quietly was to push a fix the session had already decided not to write. Measured on a batch of four PRs: seven launches across two PRs that were red on a vulnerability scan neither could have caused produced five reports of a state that could not change. The watcher now records the `check_failure` it reports, and a later launch that finds the identical head commit and failed set emits `repeat_failure` and keeps watching. The record expires after `PR_SENTINEL_DAMPEN` seconds (default 3600) because a new session has never seen that report. Any doubt about the record, such as an unreadable file, an unwritable directory, or a clock that moved backwards, falls back to waking (#136).

**[A head that predates the base's fix gets its own event](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.12.0/README.md#a-head-that-predates-the-bases-fix).** When a failing check is green on the base branch, the watcher used to call it this PR's own failure and ask the session to diagnose it. That was wrong when this head had not yet picked up the base's fix: following the advice wrote a second copy of a fix that had already landed, and then conflicted with it. The watcher now asks GitHub whether this head has the green run's commit behind it. If it doesn't, the new terminal **`base_fixed`** event says to update the branch and relaunch, with no log excerpt, because there is nothing to diagnose yet. The report doesn't claim the failure is inherited, only that the evidence for "yours" is code this head doesn't contain. When the comparison can't be read, you get `check_failure` exactly as before (#145).

**[Wake reports say what the base comparison established](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.12.0/README.md#failures-inherited-from-the-base-branch).** The comparison has four ways to find a failure "not inherited" — no Actions run behind the check, an unreadable workflow id, no completed run on the base, or `PR_SENTINEL_BASE_CHECK=0` — and only a green base run used to leave a trace in the report. Each now prints one line naming which. A mixed failed set also lists the checks found red on the base, and says the list is partial, since the comparison stops at the first check that isn't red there (#148).

**Every report names the head commit.** `ready`, `ready_watching`, `closed`, `timeout` and `error` printed no `Head SHA:`, so two watchers armed at different heads emitted byte-identical `ready` reports. A green verdict taken before a push replaced the head read exactly like one taken after it. `error` names the last head it read and marks it unconfirmed, because the read that failed may be the one that would have named it (#135).

**A stopped or relaunched watcher is no longer mistaken for a live one.** Three fixes, all on the relaunch path the guard itself prescribes. A watcher stopped with `TaskStop` was still counted as live, so the relaunch the deny told the session to make was then denied as a duplicate (#158). A launch carrying a `PR_SENTINEL_*` prefix, such as `PR_SENTINEL_WATCH_UNTIL=closed`, was not recognised as a watcher launch at all: an unattended session stalled on a permission prompt, and a relaunch could start a second watcher on a covered PR (#137). And the Stop hook kept blocking on a PR whose watcher had reported `ready` once the harness reaped the output file, if the session had read the report with `cat` rather than the Read tool. In one measured session, the block named a PR as open nearly three days after it merged (#157).

## Upgrading

**Nothing to do.** No removals, no renames, no configuration change required. A plugin install carries everything.

**Three new knobs, all optional.** `PR_SENTINEL_DAMPEN` (default `3600`) sets how long a reported failure stays dampened; `0` turns dampening off and stops the watcher writing its record. `PR_SENTINEL_STATE_DIR` (default `${TMPDIR}/pr-sentinel`) moves that record. `PR_SENTINEL_PROBE_TIMEOUT_SCALE` (default `1`) multiplies the overlap check's 5-second per-probe budget on a machine loaded enough that probes time out; it is floored at 1, so no value can shorten a budget.

**Two new event names, none removed or renamed.** The set goes from fourteen to sixteen: the terminal **`base_fixed`**, and the **`repeat_failure`** notice. A notice is not a handoff, so the Stop hook treats `repeat_failure` as it treats `base_failure`. A session matching on `PR-SENTINEL EVENT:` headers gains two values and loses none.

**Reports gain lines, and none lose them.** Five events now carry `Head SHA:`, and a wake path can now carry a line on the base comparison and a list of inherited checks. A reader that parses a report line by line sees more lines, and none of the existing ones changed.

**`base_fixed` asks for a branch update the way `behind` does.** It follows `PR_SENTINEL_HEAL`: rebase and force-push with lease by default, or merge the base in under `PR_SENTINEL_HEAL=merge`.

## Deprecations

**Nothing is deprecated, and nothing user-facing was removed.** No configuration key, event name, report field, or script path went away this window.

## Trust boundary

**One new GitHub read, and its response is wider than what it uses.** `base_fixed` asks GitHub's `compare/{base}...{head}` endpoint whether this head has the base's green commit behind it. GitHub has no narrower endpoint for that, and the response carries the intervening commits' messages, author names, and patches. `gh`'s built-in query extracts the one `status` word on your machine, and nothing else in the response is parsed, stored, printed, or passed to your session. The read happens at most once per watch, and `PR_SENTINEL_BASE_CHECK=0` switches it off. `PRIVACY.md` names it in the watcher's section.

**The watcher writes to disk for the first time.** It writes one small record per PR: a timestamp, the event name, the head commit, and the failing checks' names. The file is named from the PR's URL, and its directory is created mode `700` because the default parent is world-readable. The file name is built from characters that cannot form `.` or `..`, and a test enforces that. `PR_SENTINEL_DAMPEN=0` stops both the write and the read. Disclosed in `PRIVACY.md`, and a new test fails the build if the watcher's section stops naming the write.

**The launch auto-allow widened by one namespace, deliberately no further.** The guard now strips leading `PR_SENTINEL_*` assignments before recognising a watcher launch, and only those. A blanket strip would have auto-allowed `BASH_ENV=evil.sh bash <watcher> N`, and bash sources `BASH_ENV` before the script runs.

**The Stop hook's transcript recovery reads nothing new.** A recovered report counts only when its command names an output-file path the hook already learned from the harness or the launch command, and the rules on which part of the report may be trusted are unchanged.

**The `gh --json` field list is untouched.** It still cannot reach `body`, `comments`, `reviews`, or `title`, and `tests/test_watcher.py` still fails the build if it does.

**No security advisory accompanies this release**, and no dependency bumps: the plugin is stdlib Python and POSIX-ish bash, and depends on nothing but `gh`.
