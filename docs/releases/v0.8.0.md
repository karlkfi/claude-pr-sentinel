Wake your session on CI failures and merge conflicts — no foreground polling, no comment-channel injection.

> [!NOTE]
> **A failing check the base branch is already failing no longer wakes you.** The watcher compares each surviving failure against the same workflow's latest run on the base; when every one is inherited it reports the new `base_failure` notice and keeps polling, instead of sending you to fix somebody else's breakage. `PR_SENTINEL_BASE_CHECK=0` restores the old behaviour.

## Highlights

**[An inherited failure is now named as inherited](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.8.0/README.md#failures-inherited-from-the-base-branch).** A `check_failure` report told the session to "diagnose and fix the failing check(s) below in this local session" — an instruction that is simply wrong when the base branch is what's broken, and whose cost scales with the number of sessions you have in flight rather than with how often it happens. Every session touching a file the gate covers got the same report, each wrote its own fix, and whoever landed second paid for a rebase conflict on top. The new **`base_failure`** notice resolves each failing check's workflow, asks whether that workflow's latest completed run on the base also failed, and when **every** one did, reports the inheritance instead of the wake — naming the base run per workflow (`Also failing on main: doc-links.yml (run 31274922338, 47815b6, failure)`) and carrying no CI log excerpt, because the diagnosis belongs to whoever fixes the base.

**It holds rather than exits, so the unblock signal is the base going green.** `base_failure` is a notice, not a terminal event: the watch continues, which means it works whether the base is fixed by a standalone PR or by a revert — no dependence on somebody closing a tracking issue. If the base clears while the check is still red on your PR, that failure *is* the PR's own, and the next poll wakes you with a normal `check_failure`.

**The comparison is scoped to the workflow, never to the base branch's newest run.** A path-gated workflow only runs when its paths change, so the tip of `main` and that workflow's last run can be many commits apart — reading the tip yields a stale green from before the breakage, or a stale red long after the fix. Querying `actions/workflows/<id>/runs?branch=<base>&status=completed&per_page=1` self-corrects, because a run exists only where the paths matched. The workflow id comes from the run the failing check already links to, so no name matching is involved.

**Every uncertainty falls through to `check_failure`.** All-or-nothing and fail-safe, like the `continue-on-error` absorption it sits behind: a mixed set (one failure the base doesn't share is yours), an unresolvable run, an unreadable workflow id, a `cancelled` base run, and a base with *no* run of that workflow at all each keep today's behaviour and wake you with the full failed list.

## Upgrading

**No action required.** Nothing is removed, no configuration is renamed, and the report format and `additionalContext` shape are unchanged.

**Two changes that need no action, but will be visible.**

- **A new `base_failure` notice can reach a session** — any agent guidance that enumerates watcher events should learn it. It is a notice, not a handoff: the PR is still open and the watch continues, so the Stop hook keeps holding the session responsible (#45).
- **A check that is red on both your PR and the base stops waking you** until the base goes green. That is the point of the release, and it is the one behaviour change to be aware of if you were relying on being woken for every red check.

**One new knob**, documented in [Configuration](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.8.0/README.md#configuration):

| Variable | Default | Purpose |
|---|---|---|
| `PR_SENTINEL_BASE_CHECK` | (on) | compare each failing check against the same workflow's latest run on the base branch, and report `base_failure` instead of `check_failure` when the base is already red; `0`/`false`/empty wakes on every failure as before |

It is on by default but has an off switch that the `continue-on-error` absorption rule doesn't, because the evidence is weaker: absorption reads GitHub's own verdict on the exact run in question, while this infers across two runs.

**One known false negative:** a PR that *independently* breaks the same workflow the base is already breaking stays masked until the base goes green. That is a delay rather than a loss — the still-red check wakes you the moment the base clears — but it is the trade the knob exists to refuse. Relatedly, the match is by **workflow**, not by check: a workflow whose jobs fail for one reason on `main` and a different reason on your PR reads as inherited.

## Trust boundary

Two new reads, no new writable channel. Resolving a failing check to its workflow id and fetching that workflow's latest base-branch run are both GitHub-controlled metadata, like everything else the watcher reads. The comparison reads the run's **`.path`**, never `.name` or `.display_title` — a `run-name:` expression can interpolate a commit message or PR title into those, which is human-writable text this plugin does not ingest; a workflow file path is repo-controlled, the same trust level as the check names already in the report. There is still no comment or PR-body ingestion and no merge. The excerpt-banner split that stops a forged CI-log copy from driving Stop-hook dampening is unchanged. No security advisory accompanies this release. [PRIVACY.md](https://github.com/karlkfi/claude-pr-sentinel/blob/v0.8.0/PRIVACY.md) is updated to list both new reads.
